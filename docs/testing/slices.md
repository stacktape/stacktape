# Testing initiative: behavior slices

This is the initial 74-slice scope for the [QA initiative](initiative.md), not a list of completed reviews or a command
to replace every test. Read the [short policy](../testing.md) for ordinary work. Coordinators use this catalog to
prepare small assignments; workers need only their assigned rows and relevant source/procedure links.

The source anchors identify where to start reading, not exclusive write ownership. Several journeys share routers,
configuration and UI components. Before dispatch, inspect consumers, assign exact writable paths, and register shared
files with the coordinator. One worker owns a test; adjacent slices reuse its result and add coverage only for a
distinct contract. Split a row when its implementation would require several independent behavior contracts or a large
review. Keep IDs stable and add suffixes such as S29a/S29b instead of renumbering the plan.

H1–H7 refer to [foundation work](initiative.md#foundation-work). Every slice needs H1's command/baseline mapping; the
last column lists additional relevant helpers or slice prerequisites. Dependencies are a starting map, refined during
discovery, not a claim that every current test is blocked until a new harness exists.

“Live” means a small guarded check for externally owned behavior when qualifying that promise. It does not require a
cloud deployment for every assertion. Browser/API/database and emulator scenarios are local unless stated otherwise.
Keep current useful tests while adding missing behavior and before accepting deletions.

## Cross-slice ownership and sequencing

The coordinator owns the integrated journeys; a named slice owns each scenario's implementation:

| Integrated journey                                                   | Scenario owner                               | Contributors                                                                              |
| -------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Existing project → init/wizard → usable config → executable artifact | S06, with browser interaction in S07         | S01/S02/S04/S05, one relevant packaging family.                                           |
| Config → create → changed update → unchanged update → cleanup        | S13, with deletion/rollback contracts in S14 | S03/S09–S12/S20/S33; selected guarded live acceptance.                                    |
| CLI operation → Console HTTP → stored progress → visible result      | S46                                          | S18/S43/S44 plus the operation's owner.                                                   |
| Provider webhook → remote operation → runner → provider status       | S48                                          | S47 and S49/S50/S51; one representative integrated path plus provider-specific contracts. |
| Operational signal → issue/incident → alert → customer action        | S56                                          | S54/S55/S63/S65; live delivery sampled separately.                                        |
| Incident → requested investigation/fix → verifiable result/PR        | S58 for run lifecycle; S60 for proposed fix  | S43/S47/S49/S56/S59; automatic assessment S57 remains separate.                           |

Start with the four [pilot tasks](initiative.md#four-representative-tasks). The first 4–6 fresh slices should span both
repositories and reuse those fixtures, for example S02, S19, S37, S44, S54 and S69. Their exact order follows helper
readiness and write conflicts. Advance to deployment/provider/runner workflows after identity and process isolation are
proven. Framework builds can run independently but should not saturate the machine beside timing measurements.

These relationships are not a strict topological sort of entire features: a producer can use a reviewed synthetic event
contract before its consumer's rewrite is accepted. Make helper prerequisites executable, give each shared interface one
owner, and qualify the complete journey after integrating both sides. In particular, S56 and S65 must not block each
other merely because detection and incident handling exchange events.

Before declaring the catalog complete, map every runnable command/API surface, authored resource family, helper Lambda,
package public export and existing test runner to a primary owner. Explicitly assign unlisted entrypoints discovered
during that audit. This catches gaps a directory-based partition would miss without claiming that the initial catalog
are an exhaustive feature specification.
