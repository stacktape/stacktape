A `kinesis-stream` event runs a [Lambda function](/resources/compute/lambda-function) with batches of records from a
[Kinesis stream](/resources/messaging/kinesis-stream). Lambda reads each shard in order and keeps the position, so the
stream works for ordered, high-volume data such as clickstreams, telemetry or change events that several consumers read
independently.

For plain background jobs, an [SQS queue](/resources/triggers/sqs-events) is cheaper and simpler: it has no hourly
charge and no ordering to manage. Batch jobs accept `kinesis-stream` events too.

`kinesisStreamName` is the stream's key under `resources`. For a stream that another stack or account owns, use
`streamArn` instead. Set exactly one of the two.

Record data arrives base64-encoded:

```typescript
export default async (event: { Records: Array<{ kinesis: { data: string; partitionKey: string } }> }) => {
  for (const record of event.Records) {
    const payload = JSON.parse(Buffer.from(record.kinesis.data, 'base64').toString('utf-8'));
    console.info(record.kinesis.partitionKey, payload);
  }
};
```

After `stacktape deploy`, put a test record and read the function's logs:

```bash
aws kinesis put-record --stream-name <stream-name> --partition-key user-1 \
  --data '{"page":"/pricing"}' --cli-binary-format raw-in-base64-out
```

```bash
stacktape logs processor --stage dev
```

`stacktape param get clickStream name --stage dev --region eu-west-1` prints the stream name.

## Starting position

`startingPosition` decides where Lambda starts reading when the trigger is first created.

| Value | Reads |
|---|---|
| `TRIM_HORIZON` (default) | Every record still in the stream, oldest first |
| `LATEST` | Only records written after the trigger exists |

## Batching

Lambda invokes the function when the batch is full, when the batching window ends, or when the batch reaches the 6 MB
invocation payload limit.

| Property | Default | Maximum |
|---|---|---|
| `batchSize` | 100 | 10,000 |
| `maxBatchWindowSeconds` | 0 (no wait) | 300 |
| `parallelizationFactor` | 1 | 10 |

`parallelizationFactor` runs up to 10 batches from one shard at the same time. Records with the same partition key are
still processed in order; records with different keys may run in parallel.

### Enhanced fan-out

By default the trigger shares each shard's read throughput (2 MB/s) with every other consumer of the stream. Set
`autoCreateConsumer: true` to give it a dedicated consumer with its own throughput and lower latency. AWS charges extra
per consumer-shard hour and per GB read. If you manage the consumer yourself, pass `consumerArn` instead; the two can't
be combined.

```typescript
new KinesisIntegration({ kinesisStreamName: 'clickStream', autoCreateConsumer: true })
```

## Failures and retries

If the function throws, Lambda retries the whole batch, including records it already processed. Until the batch
succeeds, Lambda doesn't move past it, so one bad record blocks its shard. By default Lambda keeps retrying until the
record expires from the stream (24 hours unless you raise `retentionPeriodHours` on the stream). Make the handler
idempotent and give the trigger a way out:

```typescript
new KinesisIntegration({
  kinesisStreamName: 'clickStream',
  maximumRetryAttempts: 3,
  bisectBatchOnFunctionError: true,
  reportBatchItemFailures: true,
  onFailure: { arn: $ResourceParam('failedClicks', 'arn'), type: 'sqs' }
})
```

- `maximumRetryAttempts` stops retrying a batch after this many attempts.
- `bisectBatchOnFunctionError` splits a failing batch in two before each retry, which narrows it down to the bad record.
- `reportBatchItemFailures` lets the handler return `{ batchItemFailures: [{ itemIdentifier }] }` with the sequence
  number of the first record it couldn't process. Lambda then retries from that record instead of the whole batch.
  A handler that returns nothing with this setting on is treated as having processed every record.
- `onFailure` names an SQS queue or SNS topic for batches that still fail.

The `onFailure` destination receives a description of the failed batch, not the records: the shard ID, the first and
last sequence number and the error. To reprocess the records, read them from the stream by sequence number before they
expire. If you need the payloads kept longer, raise the stream's retention or have the handler save failed records to
S3 or a queue itself.

## Kinesis events FAQ

### How do I tell that the function can't keep up?

Watch the function's `IteratorAge` metric in CloudWatch. It grows when records wait longer before they're processed.
Raise `batchSize` or `parallelizationFactor`, give the function more memory, or add shards to a provisioned stream.

### Can a container consume the stream?

Not with this trigger. Run a consumer, such as the Kinesis Client Library, in a
[worker service](/resources/compute/worker-service) and give it access with
[`connectTo`](/configuration/connecting-resources).
