An HTTP trigger runs a [Lambda function](/resources/compute/lambda-function) for each request that matches a route.
There are two kinds: `http-api-gateway` routes by method and path on an
[HTTP API Gateway](/resources/networking/http-api-gateway), and `application-load-balancer` routes on paths, methods,
hosts, headers, query parameters and source IPs on an
[Application Load Balancer](/resources/networking/application-load-balancer). Containers of a
[multi-container workload](/resources/compute/multi-container-workload) and [batch jobs](/resources/compute/batch-job)
accept both too.

A [web service](/resources/compute/web-service) or a [private service](/resources/compute/private-service) gets its
traffic from its own properties, not from these triggers.

## API Gateway or load balancer

|  | HTTP API Gateway | Application Load Balancer |
|---|---|---|
| Routes on | Method and path | Paths, methods, hosts, headers, query parameters, source IPs |
| Which route wins | The most specific path | The rule with the lowest `priority` |
| Authorizers | Cognito, Lambda, IAM | None, check auth in your code |
| Cost without traffic | Nothing | Hourly charge |

Use HTTP API Gateway for Lambda APIs: you pay per request and nothing while it's idle. Use a load balancer when you
route on headers or hosts, or when you already run one for containers and want Lambda routes behind the same address.

## HTTP API Gateway

Define the gateway as a resource and point the function's integration at it:

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import {
  defineConfig,
  LambdaFunction,
  HttpApiGateway,
  HttpApiIntegration,
  JsBundleLambdaPackaging
} from 'stacktape';

export default defineConfig(() => {
  const api = new HttpApiGateway({});

  const app = new LambdaFunction({ // [!code focus]
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/handler.ts'
    }),
    // [!code focus-start]
    events: [
      new HttpApiIntegration({
        httpApiGatewayName: 'api',
        method: '*',
        path: '/{proxy+}'
      })
    ]
  });
  // [!code focus-end]

  return {
    resources: { api, app }
  };
});
`
    }
  ]}
/>

`method: '*'` with `path: '/{proxy+}'` sends every request to one function. That suits an app with its own router,
such as Hono, Express or Fastify. The deploy prints the gateway URL; `stacktape param get api url --stage dev --region
eu-west-1` prints it again. Call it with `curl <url>/anything`.

### Routes

`path` takes three shapes. The most specific match wins.

| Path | Matches |
|---|---|
| `/users` | Only `/users` |
| `/users/{id}` | One segment, available as `event.pathParameters.id` |
| `/users/{proxy+}` | Everything under `/users/` |

`method` is `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS` or `*`. To send different routes to different
functions, give each function its own integration on the same gateway.

### Payload format

`payloadFormat` sets the event shape the function receives. The default is `'1.0'`; `'2.0'` is flatter and has a
`cookies` field. Frameworks with a Lambda adapter handle both, so it matters mostly for hand-written handlers. You can
set it on the gateway for all routes, and all HTTP API routes of one function must use the same format. The
[AWS comparison](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-develop-integrations-lambda.html)
shows both shapes.

### Authorization

An `authorizer` checks the request before the function runs:

- `cognito` accepts tokens from a [user auth pool](/resources/security/user-auth-pool) and rejects the rest with `401`.
- `lambda` runs your own function to decide, and rejects with `401`.
- `aws-iam` requires requests signed with AWS credentials allowed to call `execute-api:Invoke`, and rejects the rest
  with `403`. Use it for routes that other AWS workloads call.

## Application Load Balancer

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import {
  defineConfig,
  LambdaFunction,
  ApplicationLoadBalancer,
  ApplicationLoadBalancerIntegration,
  JsBundleLambdaPackaging
} from 'stacktape';

export default defineConfig(() => {
  const alb = new ApplicationLoadBalancer({});

  const usersApi = new LambdaFunction({ // [!code focus]
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/users.ts'
    }),
    // [!code focus-start]
    events: [
      new ApplicationLoadBalancerIntegration({
        loadBalancerName: 'alb',
        priority: 10,
        paths: ['/users', '/users/*'],
        methods: ['GET', 'POST']
      })
    ]
  });
  // [!code focus-end]

  return {
    resources: { alb, usersApi }
  };
});
`
    }
  ]}
/>

The function handles `GET` and `POST` on `/users` and everything under it. A request must match every condition you
set; within a list such as `paths`, any value matches.

| Condition | Matches |
|---|---|
| `paths` | URL paths, case-sensitive, with `*` and `?` wildcards |
| `methods` | HTTP methods |
| `hosts` | The `Host` header, with wildcards such as `*.example.com` |
| `headers` | A `headerName` and a list of `values` |
| `queryParams` | A `paramName` and a list of `values` |
| `sourceIps` | Client IPs in CIDR notation |

`priority` is required. The load balancer checks rules from the lowest number up and the first match handles the
request, so a broad rule with a low number hides more specific rules behind it. Numbers must be unique per listener.
Leave gaps (10, 20, 30) so you can add rules later. Set `listenerPort` only when the load balancer has custom
listeners.

## Containers

Each container of a [multi-container workload](/resources/compute/multi-container-workload) can list `http-api-gateway`
and `application-load-balancer` events with the same properties, plus the `containerPort` that receives the traffic.
Containers also accept `network-load-balancer` events for TCP and TLS traffic, and `service-connect` and
`workload-internal` events for traffic inside the stack. The multi-container workload page shows each one.
