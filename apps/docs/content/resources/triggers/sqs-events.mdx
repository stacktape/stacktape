An `sqs` event runs a [Lambda function](/resources/compute/lambda-function) with the messages that arrive in an
[SQS queue](/resources/messaging/sqs-queue). Lambda polls the queue for you, passes the messages in batches and deletes
them when the function succeeds. Use it for background work: an API puts a job on the queue and the function processes
it at its own pace.

A queue message goes to one consumer. When several functions need the same message, publish it to an
[SNS topic](/resources/triggers/sns-events) or an [event bus](/resources/triggers/event-bus-events) instead. Batch jobs
accept `sqs` events too. A container that should read the queue itself is a
[worker service](/resources/compute/worker-service) that polls SQS in its code.

## Basic example

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import {
  defineConfig,
  LambdaFunction,
  SqsQueue,
  SqsIntegration,
  JsBundleLambdaPackaging
} from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const orderQueue = new SqsQueue({});

  const orderProcessor = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/process-orders.ts'
    }),
    events: [
      new SqsIntegration({
        sqsQueueName: 'orderQueue'
      })
    ]
  });

  return {
    resources: { orderQueue, orderProcessor }
  };
});
// [!code focus-end]
`
    }
  ]}
/>

`sqsQueueName` is the queue's key under `resources`. For a queue that another stack or tool manages, use
`sqsQueueArn` instead. Set exactly one of the two.

The function receives the standard Lambda SQS event. Each record has the message `body` as a string and a `messageId`:

```typescript
export default async (event: { Records: Array<{ messageId: string; body: string }> }) => {
  for (const record of event.Records) {
    const order = JSON.parse(record.body);
    // Replace the log line with your own processing, such as saving the order.
    console.info(`Processed order ${order.orderId}, message ${record.messageId}`);
  }
};
```

After `stacktape deploy`, send a test message and check that the function processed it. Print the queue URL:

```bash
stacktape param get orderQueue url --stage dev --region eu-west-1
```

Send a message to that URL, in place of `<queue-url>`. The command prints the message's `MessageId`:

```bash
aws sqs send-message --region eu-west-1 --queue-url <queue-url> --message-body '{"orderId":"42"}'
```

Read the function's logs. A line `Processed order 42, message <MessageId>` with the same ID means the message was
consumed:

```bash
stacktape logs orderProcessor --stage dev --region eu-west-1
```

## Batching

Lambda invokes the function when the batch is full, when the batching window ends, or when the batch reaches the 6 MB
invocation payload limit, whichever comes first.

| Property | Standard queue | FIFO queue |
|---|---|---|
| `batchSize` | 10 by default, up to 10,000 | 10 by default, up to 10 |
| `maxBatchWindowSeconds` | Off by default, up to 300 | Not supported |

AWS needs a batching window of at least 1 second for a `batchSize` above 10. A larger batch with a window means fewer
invocations and a lower Lambda bill, at the cost of latency:

```typescript
new SqsIntegration({ sqsQueueName: 'orderQueue', batchSize: 100, maxBatchWindowSeconds: 30 })
```

This waits up to 30 seconds to collect 100 messages. If 100 messages arrive in 5 seconds, the function runs right away.

### Limiting concurrency

`maximumConcurrency` (2 to 1000) caps how many copies of the function the queue runs at once. Use it to protect a
database or a rate-limited API. Messages wait in the queue while the cap is reached.

```typescript
new SqsIntegration({ sqsQueueName: 'orderQueue', maximumConcurrency: 5 })
```

To see that the queue is falling behind, watch `ApproximateNumberOfMessagesVisible` (backlog) and
`ApproximateAgeOfOldestMessage` (lag) in CloudWatch. The queue can alarm on its backlog with the
`sqs-queue-received-messages-count` or `sqs-queue-not-empty` [alarm](/observability/alarms). When the backlog keeps
growing, raise `batchSize` or remove a `maximumConcurrency` cap.

## Failures and retries

If the function throws, the whole batch goes back to the queue. It becomes visible again when the queue's visibility
timeout ends (30 seconds by default) and Lambda delivers it again. Messages also arrive more than once now and then,
even without errors, so write the handler to be idempotent: processing the same `messageId` twice must not charge a card
twice.

The function's `timeout` can't be longer than the queue's `visibilityTimeoutSeconds`, or AWS refuses the trigger.
Stacktape checks this before deploying and stops with:

<Error>
Error in `function` `orderProcessor`: its `timeout` (60 s) is longer than the visibility timeout of its trigger queue
`orderQueue` (30 s, the default). AWS refuses such a trigger, because a message would become visible to other
consumers while the function still processes it.
</Error>

Raise `visibilityTimeoutSeconds` on the queue or lower the function's `timeout`. AWS recommends a visibility timeout of
six times the function timeout.

### Send failing messages to a dead-letter queue

Without a limit, a message that always fails is retried until the queue's retention period ends (4 days by default).
Set a `redrivePolicy` on the queue to move it to a second queue after a number of receives:

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, LambdaFunction, SqsQueue, SqsIntegration, JsBundleLambdaPackaging } from 'stacktape';

export default defineConfig(() => {
  // [!code focus-start]
  const failedOrders = new SqsQueue({});
  const orderQueue = new SqsQueue({
    redrivePolicy: { targetSqsQueueName: 'failedOrders', maxReceiveCount: 5 }
  });
  // [!code focus-end]

  const orderProcessor = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({ entryfilePath: './src/process-orders.ts' }),
    events: [new SqsIntegration({ sqsQueueName: 'orderQueue' })]
  });

  return { resources: { failedOrders, orderQueue, orderProcessor } };
});
`
    }
  ]}
/>

A dead-letter queue for a FIFO queue must also be FIFO.

### Retry only the failed messages

With `reportBatchItemFailures: true`, the function returns the IDs of the messages it couldn't process. Only those go
back to the queue; Lambda deletes the rest.

```typescript
new SqsIntegration({ sqsQueueName: 'orderQueue', reportBatchItemFailures: true })
```

For a standard queue, try every message and collect the failures:

```typescript
export default async (event: { Records: Array<{ messageId: string; body: string }> }) => {
  const batchItemFailures: Array<{ itemIdentifier: string }> = [];
  for (const record of event.Records) {
    try {
      await saveOrder(JSON.parse(record.body));
    } catch {
      batchItemFailures.push({ itemIdentifier: record.messageId });
    }
  }
  return { batchItemFailures };
};
```

For a FIFO queue, stop at the first failure and return that message and every message after it. Otherwise a later
message of the same group is processed before the one that failed, and the order is lost.

```typescript
export default async (event: { Records: Array<{ messageId: string; body: string }> }) => {
  for (const [index, record] of event.Records.entries()) {
    try {
      await saveOrder(JSON.parse(record.body));
    } catch {
      return {
        batchItemFailures: event.Records.slice(index).map(({ messageId }) => ({ itemIdentifier: messageId }))
      };
    }
  }
  return { batchItemFailures: [] };
};
```

Turn the setting on only for handlers that return this shape. With it on, a handler that returns nothing tells Lambda
that every message succeeded, so a failure it swallowed is lost.
