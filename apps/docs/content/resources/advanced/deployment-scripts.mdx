A `deployment-script` is a Lambda function that Stacktape runs during a deploy (`after:deploy`) or before a delete
(`before:delete`). Use it for work that must run inside AWS at that moment: database migrations, seed data, search
index mappings, cleanup before a stack is removed. With `connectTo` and `joinDefaultVpc` it can reach databases in the
stack's VPC.

Work that runs on your machine or CI runner, such as builds, belongs in [hooks](/configuration/hooks-and-scripts). Work
longer than 15 minutes needs a [batch job](/resources/compute/batch-job). The
[lifecycle guide](/configuration/hooks-and-scripts#choose-the-right-tool) compares the options for migrations.

## Basic example

This script runs the database migrations after every deploy:

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import {
  defineConfig,
  DeploymentScript,
  RelationalDatabase,
  RdsEnginePostgres,
  JsBundleLambdaPackaging,
  $Secret
} from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const mainDatabase = new RelationalDatabase({
    engine: new RdsEnginePostgres({ version: '16', primaryInstance: { instanceSize: 'db.t4g.micro' } }),
    credentials: { masterUserPassword: $Secret('main-database-password') }
  });

  const migrate = new DeploymentScript({
    trigger: 'after:deploy',
    packaging: new JsBundleLambdaPackaging({ entryfilePath: './scripts/migrate.ts' }),
    connectTo: ['mainDatabase'],
    joinDefaultVpc: true,
    timeout: 300
  });

  return {
    resources: { mainDatabase, migrate }
  };
});
// [!code focus-end]
`
    }
  ]}
/>

Create the password secret once per region before the first deploy:

```bash
stacktape secret set main-database-password --region eu-west-1
```

`connectTo` injects `STP_MAIN_DATABASE_CONNECTION_STRING`; `joinDefaultVpc` puts the script in the VPC so it can reach
the database. Set `timeout` explicitly: the default is 10 seconds, and the maximum is 900.

The script must bring its migration code with it. The bundle contains only what `migrate.ts` imports, so a CLI such as
`prisma migrate` or a folder of `.sql` files isn't there unless you add it. This script keeps the migrations as imported
TypeScript and runs each one in a transaction with the `postgres` package, recording what ran:

```typescript
// scripts/migrations.ts
export const migrations = [
  { id: '001_create_users', sql: 'CREATE TABLE users (id uuid PRIMARY KEY, email text NOT NULL UNIQUE)' },
  { id: '002_add_user_name', sql: 'ALTER TABLE users ADD COLUMN name text' }
];
```

```typescript
// scripts/migrate.ts
import postgres from 'postgres';
import { migrations } from './migrations';

export default async () => {
  const sql = postgres(process.env.STP_MAIN_DATABASE_CONNECTION_STRING!, { ssl: 'require' });
  try {
    await sql`CREATE TABLE IF NOT EXISTS schema_migrations (id text PRIMARY KEY, applied_at timestamptz NOT NULL DEFAULT now())`;
    for (const migration of migrations) {
      await sql.begin(async (tx) => {
        const [done] = await tx`SELECT 1 FROM schema_migrations WHERE id = ${migration.id}`;
        if (done) return;
        await tx.unsafe(migration.sql);
        await tx`INSERT INTO schema_migrations (id) VALUES (${migration.id})`;
      });
    }
  } finally {
    await sql.end();
  }
};
```

If a migration fails, its transaction rolls back and the earlier ones stay recorded, so the next run continues where
this one stopped. A migration tool that runs in-process, such as Drizzle's or Knex's migrator, works the same way; add
its migration files to the bundle with `includeFiles` on the packaging.

## When it runs and what a failure does

An `after:deploy` script runs on every deploy, after every other resource in the stack has been created or updated.
By then your new application code is already deployed and serving traffic, so for the length of the migration the new
code runs against the old schema.

If the script fails, the deploy fails:

- By default, the stack stays in `UPDATE_FAILED` with everything that already updated, including the new code. Fix the
  script and deploy again, or run [`stacktape stack recover`](/cli/stack-recover) to return the stack to its previous
  version.
- With `deploymentConfig.autoRollback: true`, CloudFormation returns the infrastructure and the code to the previous
  version automatically.

Neither undoes what the script already wrote to the database. A rollback only means the old code runs against whatever
schema the script left behind. So:

- Make each migration work with both the old and the new code: add columns and tables, don't rename or drop them.
- Deploy the code that needs the new schema in the next release, after the migration is in.
- Drop old columns in a later release still, once no deployed code reads them.

### before:delete

A `before:delete` script runs at the start of [`stacktape delete`](/cli/delete), before any resource is removed. Use it
to export data or unregister webhooks. If it fails, the stack ends in `DELETE_FAILED` with the script's error. Fix the
script, or catch the errors you can live with inside it, and run the delete again.

```typescript
new DeploymentScript({
  trigger: 'before:delete',
  packaging: new JsBundleLambdaPackaging({ entryfilePath: './scripts/cleanup.ts' }),
  timeout: 300
})
```

## Run a script manually

```bash
stacktape deployment-script run migrate --stage dev --region eu-west-1
```

The command rebuilds the script from your local code, **replaces the code of the deployed script Lambda** with it,
resolves `parameters` from your local config and invokes it. So it runs the code in your working directory, not the
last deployed version, and that code stays deployed afterwards. Changes to `environment`, `connectTo`, memory, timeout
or VPC settings still need a [`deploy`](/cli/deploy). See [`deployment-script run`](/cli/deployment-script-run).

## Packaging

| Type | When to use |
|------|-------------|
| [`js-bundle`](/packaging/function/js-bundle) | JavaScript and TypeScript. Stacktape bundles the entry file and what it imports. |
| [`buildpack`](/packaging/function/buildpack) | Python, Java, Go, Ruby, .NET or Rust. |
| [`custom-artifact`](/packaging/function/custom-artifact) | A zip or directory you built yourself, with `handler` in `file:function` format. |

Stacktape picks the Lambda runtime from the file extension unless you set `runtime`. `memory` takes 128 to 10,240 MB
(more memory also means more CPU), and `storage` sets the `/tmp` space from 512 MB (the default) to 10,240 MB.

## Connecting to resources

`connectTo` grants the script access to resources in the stack and injects their parameters as
`STP_<RESOURCE_NAME>_<PARAMETER>` variables, for example `STP_MAIN_DATABASE_CONNECTION_STRING`. See
[Connecting resources](/configuration/connecting-resources) for what each resource provides.

Databases and Redis run in the VPC, so the script also needs `joinDefaultVpc: true`. A Lambda function in the VPC has
no internet access unless the VPC has NAT (see `stackConfig.nat`). If the script must call an outside API too, set up
NAT or split it into two scripts. For AWS services that `connectTo` doesn't cover, add `iamRoleStatements`.

## Environment and parameters

- `environment` sets environment variables. Put secrets here with [`$Secret()`](/configuration/directives).
- `parameters` is passed to the handler as its event. Don't put secrets in it: the values are stored in the stack
  template.

```typescript
new DeploymentScript({
  trigger: 'after:deploy',
  packaging: new JsBundleLambdaPackaging({ entryfilePath: './scripts/seed.ts' }),
  environment: { ADMIN_EMAIL: $Secret('admin-email') },
  parameters: { seedCount: 100 },
  timeout: 60
})
```

```typescript
export default async (event: { seedCount: number }) => {
  console.info(`Seeding ${event.seedCount} rows for ${process.env.ADMIN_EMAIL}`);
};
```

Script logs are in CloudWatch like any function's. A deployment script runs on Lambda pricing; a 10-second migration at
512 MB costs a fraction of a cent.
