An `email-sender` gives your workloads a verified Amazon SES identity to send email from: a domain or one email
address. Stacktape verifies the identity, sets up DKIM and bounce handling, and grants connected workloads permission
to send from it and nothing more.

## Basic example

```yaml
resources:
  mail:
    type: email-sender
    properties:
      identity: example.com

  sendWelcomeEmail:
    type: function
    properties:
      packaging:
        type: js-bundle
        properties:
          entryfilePath: src/send-welcome-email.ts
      connectTo:
        - mail
```

```ts
import { SESv2Client, SendEmailCommand } from '@aws-sdk/client-sesv2';

const ses = new SESv2Client({ region: process.env.STP_MAIL_REGION });

export const handler = async () => {
  await ses.send(new SendEmailCommand({
    FromEmailAddress: `hello@${process.env.STP_MAIL_IDENTITY}`,
    Destination: { ToAddresses: ['customer@example.net'] },
    ConfigurationSetName: process.env.STP_MAIL_CONFIGURATION_SET_NAME,
    Content: {
      Simple: {
        Subject: { Data: 'Welcome' },
        Body: { Text: { Data: 'Thanks for joining us.' } }
      }
    }
  }));
};
```

`connectTo` injects `IDENTITY`, `IDENTITY_ARN`, `REGION`, `CONFIGURATION_SET_NAME` and `FEEDBACK_TOPIC_ARN` (here
`STP_MAIL_IDENTITY` and so on). It grants `ses:SendEmail` and `ses:SendRawEmail` on that identity and configuration set
only, and no SES administration.

## Verification and DNS

For a domain, Stacktape sets up 2048-bit Easy DKIM. If the domain has a public Route 53 hosted zone that the domain is
actually delegated to, Stacktape creates the three DKIM CNAME records. A hosted zone that exists but isn't delegated
doesn't count.

With DNS elsewhere, the deploy succeeds while verification is pending and prints the three CNAME names and values. Add
them at your DNS provider. For a single email address, SES sends a verification link to that mailbox instead.

<Warning>
SES identities and the SES sandbox are per region. In the sandbox you can send only to verified recipients, with low
daily limits. Stacktape warns and links to the production access request, but doesn't block the deploy. Request
production access before you send to customers.
</Warning>

## Shared identity

An SES identity belongs to the AWS account and region, not to one project or stage. Stacktape creates it in a separate
shared CloudFormation stack with termination protection, one per identity. Every project and stage in that account and
region that uses `example.com` shares it; `billing@example.com` is a different identity.

Deleting a project's stack doesn't delete the shared stack, and the delete output lists it as retained. Stacktape
doesn't remove unused shared identities for you.

The shared stack also has:

- a configuration set that suppresses addresses that bounced or complained;
- an SNS topic for feedback;
- a destination that publishes `BOUNCE` and `COMPLAINT` events to that topic.

Because they're shared, a feedback subscriber sees the feedback for every send from that identity, including other
projects and stages. Make feedback processing idempotent.

## Handle bounces and complaints

Subscribe a function to the feedback topic with an [SNS event](/resources/triggers/sns-events):

```yaml
resources:
  mail:
    type: email-sender
    properties:
      identity: example.com

  processEmailFeedback:
    type: function
    properties:
      packaging:
        type: js-bundle
        properties:
          entryfilePath: src/process-email-feedback.ts
      events:
        - type: sns
          properties:
            snsTopicArn: $ResourceParam('mail', 'feedbackTopicArn')
```

## Use an identity managed elsewhere

Set `manageIdentity: false` to use an identity that another tool created. Stacktape checks that the exact identity
exists, but never takes it over, changes it or widens it to a parent domain.

```yaml
resources:
  mail:
    type: email-sender
    properties:
      identity: billing@example.com
      manageIdentity: false
      configurationSetName: centrally-managed-mail
```

`configurationSetName` is optional. When you set it, Stacktape checks that it exists and limits the send permission to
it. External identities don't get Stacktape's feedback topic; set up feedback where the identity is managed.

## What it doesn't set up

Custom MAIL FROM domains, DMARC records, your own DKIM keys, SES templates, bulk sending, inbound email, dedicated IPs,
Virtual Deliverability Manager and multi-region identities. Add those with
[raw CloudFormation resources](/resources/advanced/raw-cloudformation-resources) and `iamRoleStatements`.
