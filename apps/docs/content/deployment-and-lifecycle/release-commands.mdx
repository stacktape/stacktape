# Release commands

Set `releaseCommand` on a service, a function or a server-rendered site to run a command once during a deploy, before your services and functions get the new code. Use it for database migrations. By default, it runs on every deploy that changes the image; with [`runWhenChanged`](#run-it-only-when-something-changed), only when your migration files change.

```yaml configExample="complete"
resources:
  database:
    type: relational-database
    properties:
      credentials:
        masterUserPassword: $Secret('database-password')
      engine:
        type: postgres
        properties:
          version: '17'
          primaryInstance:
            instanceSize: db.t4g.micro
      accessibility:
        accessibilityMode: vpc
  api:
    type: web-service
    properties:
      packaging:
        type: buildpack
        properties:
          sourceDirectoryPath: .
          startCommand: npm start
      resources:
        cpu: 0.25
        memory: 512
      connectTo:
        - database
      releaseCommand: npx prisma migrate deploy
```

Stacktape runs the command in a one-off ECS task. The task uses the image you are about to deploy, with the same environment variables, secrets, IAM role and network access as the service, so it reaches a database with no public address without a bastion. The deploy waits for the task and prints its logs. If the command fails, the deploy stops and your running containers keep serving the old code.

## What your commands must allow

- **The old code runs against the new schema until the rollout finishes.** Keep migrations compatible with it. To remove a column, stop using it in one deploy and remove it in a later one.
- **A retry runs the command again.** Stacktape records a run only when the whole deploy succeeds, so a deploy that fails after the command succeeded runs it again on the next attempt. Migration tools handle this already, because they record what they applied.
- **Nothing reverses the command.** Neither a failed deploy nor [`stacktape rollback`](/deployment-and-lifecycle/rollbacks) changes the database back. A rollback does not run the command either, because an old command must not run against a newer database. The old code has to work with the schema that is there.

## Run it only when something changed

By default, the command runs on each deploy that changes the image. Use `runWhenChanged` to run it only when the listed files or directories changed:

```yaml
releaseCommand:
  command: npx prisma migrate deploy
  runWhenChanged:
    - prisma/migrations
```

A deploy that changes none of the listed paths skips the command and takes no extra time. Use this with tools that apply only what is in one folder. Don't use it with a command that reads anything else that can change. Paths are relative to the project root, and each one must exist.

The command also runs when the environment variables or secrets of the service change through a CloudFormation deployment, even if the listed paths stayed the same. A replaced database therefore gets its schema.

## How it affects deploy time

| Deploy | Added time |
|---|---|
| The command does not run | None |
| Fast deployment, the command runs | About 15 to 30 seconds for the task to start, plus the command |
| Full deployment, the command runs | The same, inside the CloudFormation update |
| A function or site, the command runs | The image build, the task start and the command, inside a CloudFormation update |

A code-only deploy stays a [fast deployment](/deployment-and-lifecycle/deploying-stacks), and it runs the command before it updates any service. With [code swap](/deployment-and-lifecycle/code-swap), the command runs from the new image and the swap follows.

## Options

| Option | Default | Description |
|---|---|---|
| `command` | | The shell command. It runs through `/bin/sh -c` in place of the image's entry point. If the image needs its entry point, call it in the command. An image without a shell cannot run a release command. |
| `runWhenChanged` | | Files or directories that decide whether the command runs. |
| `timeout` | `3300` | Seconds the command can run, up to 3300. After that, the task stops and the deploy fails. |
| `container` | The main container | The container to run in. Required for a [multi-container workload](/resources/compute/multi-container-workload) with several containers. Not allowed on a function or site. |

Containers that the chosen container depends on run too, but only the chosen container decides when the task ends. Load balancers, health checks and scaling don't apply to the task.

## Several commands

Each service can have its own release command. They run one at a time, in the order of the resources in your config. Every container service and function waits until all of them finished.

One exception: if a command refers to a workload, for example through an environment variable with its URL, that workload has to be updated first, so it can get new code before the command finishes. The deploy prints a warning that names it.

## Functions and server-rendered sites

A [function](/resources/compute/lambda-function) and a server-rendered site, such as [`nextjs-web`](/resources/frontend/nextjs), take `releaseCommand` too. Their packages hold only bundled code, so Stacktape builds an image of the whole project and runs the command from the project root in a one-off ECS task. The task gets the resource's environment variables and its access to the resources in `connectTo`, and it runs in the stack's VPC, so it reaches a database with no public address.

```yaml
resources:
  database:
    type: relational-database
    properties:
      credentials:
        masterUserPassword: $Secret('database-password')
      engine:
        type: postgres
        properties:
          version: '17'
          primaryInstance:
            instanceSize: db.t4g.micro
  api:
    type: function
    properties:
      packaging:
        type: js-bundle
        properties:
          entryfilePath: src/api.ts
      connectTo:
        - database
      releaseCommand:
        command: npx prisma migrate deploy
        runWhenChanged:
          - prisma/migrations
```

Three things differ from a service:

- **Building the image needs Docker** on the machine that deploys, each time the command is due. Set `runWhenChanged`: without it, each change of the project builds the image and runs the command.
- **A deploy that runs the command goes through CloudFormation.** A deploy that skips it stays a fast deployment.
- **The task has 1 vCPU and 2 GB of memory**, whatever the function has. Nothing runs between deploys, so it costs only the seconds the command takes.

If the machine that deploys has no Docker, run the migration from an [`afterDeploy` hook](/configuration/hooks-and-scripts) instead.

## `js-bundle` services

A `js-bundle` image contains only the bundled code, not your migration tool or migration files. For these services, Stacktape builds a second image of the whole project, used only by the release command. It builds it only when the command is due, so ordinary code deploys keep the fast bundle. Use `runWhenChanged` with these services: without it, each code change builds the second image and runs the command.

## Skipping and interrupting

Pass `--skip-release-command` to deploy without running the command, for example when you ran it yourself or when you need to deploy a fix for it. A skipped run is not recorded, so the next deploy without the flag runs the command if its inputs still differ from the last successful run.

If you cancel a deploy while the command runs, its task keeps running, because stopping a migration partway can leave the database half migrated. The next deploy waits for that task to finish before it runs the command again or changes anything, and prints which task it waits for. It stops waiting after the command's `timeout`.

## Logs

The output appears in the deploy output, prefixed with the service name. It is also kept in the `stp-release` log group of the service, even when the service's own logging is disabled. Use the `logs-release-command` link in the stack details to open it.

## When to use something else

Use an [`afterDeploy` hook](/deployment-and-lifecycle/deployment-scripts-and-hooks) for a command that needs the new code to be live, such as seeding through your API or warming a cache. A hook runs on your machine or CI runner, after the deploy, and a failed hook fails the command without undoing the deployment.
