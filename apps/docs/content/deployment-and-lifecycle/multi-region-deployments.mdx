# Multi-region deployments

A Stacktape stack lives in one AWS region. To run in several regions, deploy the same config once per region. Each deploy creates an independent stack with its own compute, databases and network; Stacktape does not connect them.

Most apps do not need this. A single region with a [CDN](/resources/networking/cdn) in front serves static and cacheable content fast worldwide. Go multi-region when dynamic requests are too slow for distant users, when regulations require data to stay in a country or region, or when a regional AWS outage must not take your product down. Every region adds the full cost of its stack, plus replication and routing you set up yourself.

## Deploy to two regions

```bash
stacktape deploy --stage production --region eu-west-1
```

```bash
stacktape deploy --stage production --region us-east-1
```

The same stage name can exist in several regions; the stacks do not collide. If the config declares a `region`, `--region` overrides it for that command.

Stacktape supports these regions: `us-east-1`, `us-east-2`, `us-west-1`, `us-west-2`, `ca-central-1`, `sa-east-1`, `eu-west-1`, `eu-west-2`, `eu-west-3`, `eu-central-1`, `eu-north-1`, `eu-south-1`, `ap-east-1`, `ap-south-1`, `ap-northeast-1`, `ap-northeast-2`, `ap-northeast-3`, `ap-southeast-1`, `ap-southeast-2`, `me-south-1` and `af-south-1`. The CLI refuses others, even when your account has them enabled. Regions that AWS launched as opt-in, such as `ap-east-1` or `me-south-1`, also need to be enabled in your account, and not every AWS service is available in every region.

## Vary the config by region

One config usually works in every region. When something must differ, such as instance sizes or a feature that only one region has, read `region` in the `defineConfig` callback:

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, WebService, JsBundleImagePackaging } from 'stacktape';

// [!code focus-start]
export default defineConfig(({ region, stage }) => {
  const isMainRegion = region === 'eu-west-1';

  const api = new WebService({
    packaging: new JsBundleImagePackaging({
      entryfilePath: './src/server.ts'
    }),
    resources: {
      cpu: stage === 'production' && isMainRegion ? 1 : 0.5,
      memory: stage === 'production' && isMainRegion ? 2048 : 1024
    }
  });

  return { resources: { api } };
});
// [!code focus-end]`
    }
  ]}
/>

The other values the callback receives are listed in [Configuration files](/configuration/configuration-files#the-defineconfig-callback). For a single value, the [`$Region()` directive](/configuration/directives) is often enough.

## Patterns

- **Active-active.** Every region serves traffic. Route users to the nearest region with Route 53 latency or geolocation routing, and replicate data between regions. The most expensive and the most complex.
- **Active-passive.** One region serves traffic and the other waits, often scaled down. Route 53 failover routing switches traffic when health checks fail. Only one region writes data, so consistency is simpler, but a failover takes the DNS TTL plus the health check time.
- **One region per audience.** EU customers use `eu-west-1`, US customers `us-east-1`, each with its own data. No replication is needed. This is the usual answer to data-residency requirements.

## Data and DNS

Each region's databases, buckets and caches are separate. Stacktape does not replicate between them. AWS offers:

| Strategy | Consistency | Good for |
| --- | --- | --- |
| DynamoDB global tables | Eventual | Sessions, preferences, feature flags |
| Aurora Global Database | One writer, asynchronous replicas | Read-heavy apps that write in one region |
| S3 Cross-Region Replication | Eventual | Uploads, static assets, backups |
| Replication in your app | What you build | Selective or business-specific sync |

Replication costs extra: replicated writes in DynamoDB, the secondary Aurora cluster, cross-region data transfer.

Each regional stack can have its own [custom domain](/resources/networking/custom-domains). Routing between regions (latency, geolocation, weighted or failover records) lives outside the regional stacks. Create it in Route 53 directly, or in a separate stack with [raw CloudFormation resources](/resources/advanced/raw-cloudformation-resources).

## Automate the deploys

Run one `stacktape deploy` per region, for example as a matrix job in your pipeline; see [Custom CI/CD](/ci-cd-and-gitops/custom-ci-cd). Each job is independent: a failed deploy in one region does not affect the others, and the regions can briefly run different versions.

To keep deploys out of other regions, add a `region-restriction` [guardrail](/guardrails/deployment#region-restriction):

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, LambdaFunction, JsBundleLambdaPackaging } from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const api = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/api.ts'
    })
  });

  return {
    guardrails: [
      {
        type: 'region-restriction',
        properties: {
          allowedRegions: ['eu-west-1', 'eu-central-1', 'us-east-1']
        }
      }
    ],
    resources: { api }
  };
});
// [!code focus-end]`
    }
  ]}
/>

A deploy to another region fails before anything is built or uploaded.

## Operate each region

Every command takes the region of the stack it works on:

```bash
stacktape logs api --stage production --region us-east-1
```

Logs, metrics and alarms belong to their region. To remove a region, delete its DNS records first, then run `stacktape delete` with that region, so no record points at a stack that is being deleted.
