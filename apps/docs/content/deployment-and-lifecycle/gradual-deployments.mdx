# Gradual deployments

A gradual deployment moves traffic to the new version in steps, for example 10% first and the rest after 5 minutes, instead of switching everything at once. It works for [Lambda functions](/resources/compute/lambda-function), and for [web services](/resources/compute/web-service) and [multi-container workloads](/resources/compute/multi-container-workload) behind an [application load balancer](/resources/networking/application-load-balancer). AWS CodeDeploy shifts the traffic.

Shifting traffic alone does not detect a broken version. A rollout goes back to the old version only when a test function you write reports a failure, or when a CloudWatch alarm you name fires. See [What rolls a rollout back](#what-rolls-a-rollout-back).

## Turn it on for a function

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, LambdaFunction, JsBundleLambdaPackaging } from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const checkNewVersion = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/check-new-version.ts'
    }),
    timeout: 60
  });

  const api = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/handler.ts'
    }),
    deployment: {
      strategy: 'Canary10Percent5Minutes',
      beforeAllowTrafficFunction: 'checkNewVersion'
    }
  });

  return { resources: { checkNewVersion, api } };
});
// [!code focus-end]`
    }
  ]}
/>

On each deploy that changes `api`, CodeDeploy first runs `checkNewVersion`. If it reports success, 10% of invocations go to the new version, and after 5 minutes the rest. If it reports a failure, no traffic moves and the deploy fails.

A function with `deployment` always deploys through CloudFormation, so code changes to it are not [fast deploys](/deployment-and-lifecycle/deploying-stacks#fast-deployments). The deploy takes at least as long as the strategy.

## Turn it on for a web service

A web service needs `loadBalancing.type: 'application-load-balancer'`. The default HTTP API Gateway and a network load balancer cannot split traffic.

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, WebService, JsBundleImagePackaging } from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const api = new WebService({
    packaging: new JsBundleImagePackaging({
      entryfilePath: './src/server.ts'
    }),
    resources: { cpu: 0.25, memory: 512 },
    loadBalancing: {
      type: 'application-load-balancer'
    },
    deployment: {
      strategy: 'Canary10Percent5Minutes'
    }
  });

  return { resources: { api } };
});
// [!code focus-end]`
    }
  ]}
/>

An application load balancer costs about $16 a month plus usage in us-east-1, while an HTTP API Gateway is billed only per request. During the shift, the old and new containers run side by side, so you pay for both for the length of the strategy. Container services with `deployment` use blue/green deployment, which also rules out fast deploys for them.

`beforeAllowTrafficFunction` and `afterTrafficShiftFunction` work for services too. Before production traffic moves, CodeDeploy sends test traffic to the new containers on the load balancer's test listener, port 8080 by default (change it with `testListenerPort`). Your test function can call the load balancer on that port to check the new version.

## Strategies

| Strategy | Functions | Services | What it does |
| --- | --- | --- | --- |
| `Canary10Percent5Minutes` | Yes | Yes | 10%, then the rest after 5 minutes |
| `Canary10Percent10Minutes` | Yes | No | 10%, then the rest after 10 minutes |
| `Canary10Percent15Minutes` | Yes | Yes | 10%, then the rest after 15 minutes |
| `Canary10Percent30Minutes` | Yes | No | 10%, then the rest after 30 minutes |
| `Linear10PercentEvery1Minute` | Yes | No | 10% more every minute |
| `Linear10PercentEvery1Minutes` | No | Yes | 10% more every minute |
| `Linear10PercentEvery2Minutes` | Yes | No | 10% more every 2 minutes |
| `Linear10PercentEvery3Minutes` | Yes | Yes | 10% more every 3 minutes |
| `Linear10PercentEvery10Minutes` | Yes | No | 10% more every 10 minutes |
| `AllAtOnce` | Yes | Yes | Everything at once, after the test function |

The one-minute linear strategy is spelled `Minute` for functions and `Minutes` for services; these are AWS's names. Percentages and intervals are fixed.

Start with `Canary10Percent5Minutes`. Use a longer canary when your traffic is low and 5 minutes would not send enough requests to the new version to notice errors. Use a linear strategy when problems show only under load, such as connection pools running out. Use `AllAtOnce` to get the test function without a slow rollout.

## What rolls a rollout back

- **The `beforeAllowTrafficFunction` reports `Failed`**, or does not report within an hour. No production traffic has reached the new version yet.
- **The `afterTrafficShiftFunction` reports `Failed`.** By then all traffic is on the new version; for a function, CodeDeploy points it back to the old version.
- **A CloudWatch alarm listed in `deploymentConfig.triggerRollbackOnAlarms` fires** while CloudFormation updates the stack, which includes the shift. CloudFormation then rolls the whole stack back. This is how you roll back on errors seen by real traffic: create an alarm on the function's or the load balancer's error rate and list its ARN. See [Automatic rollback](/deployment-and-lifecycle/deploying-stacks#automatic-rollback).

Without one of these, a version that returns errors still gets all the traffic when the strategy ends.

### Write a test function

The function receives a deployment ID and a hook execution ID, runs your checks and reports the result to CodeDeploy. Stacktape gives it permission to report. Set a `timeout` long enough for your checks.

```ts
import { CodeDeployClient, PutLifecycleEventHookExecutionStatusCommand } from '@aws-sdk/client-codedeploy';

const codeDeploy = new CodeDeployClient({});

export const handler = async (event: { DeploymentId: string; LifecycleEventHookExecutionId: string }) => {
  let status: 'Succeeded' | 'Failed' = 'Succeeded';
  try {
    await runChecks(); // your checks: call the new version, check a dependency
  } catch (error) {
    console.error(error);
    status = 'Failed';
  }
  await codeDeploy.send(
    new PutLifecycleEventHookExecutionStatusCommand({
      deploymentId: event.DeploymentId,
      lifecycleEventHookExecutionId: event.LifecycleEventHookExecutionId,
      status
    })
  );
};
```

AWS describes the event and the response in [AppSpec hooks for Lambda deployments](https://docs.aws.amazon.com/codedeploy/latest/userguide/reference-appspec-file-structure-hooks.html).
