# AWS permissions

Connecting an AWS account to the Console creates one CloudFormation stack in it. The stack holds an IAM role that the Console assumes to deploy your stacks and read their logs, metrics and costs. This page says exactly what the stack creates, who can use the role and how to limit or remove it. [Connecting your AWS account](/stacktape-console/connecting-your-aws-account) covers the steps.

The CLI without an account doesn't use any of this: it deploys with your own AWS credentials.

## What the connection stack creates

The stack is created in `eu-west-1`, whatever regions you deploy to. It holds:

- **The role Stacktape assumes.** Only Stacktape's AWS account can assume it, and only with an external ID unique to this connection. Sessions last at most 12 hours.
- **A cost report bucket**, `stacktape-cur-<connection ID>`. AWS writes the account's Cost and Usage Reports there, and Stacktape reads them for the [cost pages](/managing-costs/dashboards). Reports are deleted after 30 days, and the bucket blocks public access.
- **A reporting policy** that lets the role manage the cost report definition, read the bucket, list CloudFormation stacks and turn on cost allocation tags.

Connecting is free, and the role costs nothing in AWS. The cost report bucket is billed as normal S3 storage and holds at most 30 days of reports.

## Deploy access or read-only

The role gets one of two AWS managed policies:

| Access | AWS policy | Stacktape can |
|---|---|---|
| **Can deploy** | `AdministratorAccess` | Deploy, update and delete your stacks, and read their logs, metrics and costs |
| **Read-only** | `ReadOnlyAccess` | Read logs, metrics and costs. Deploys, budgets and other writes fail. |

A connection made in the Console or with `stacktape connect` can deploy. The connection stack's `StacktapeConnectionMode` parameter decides: `PRIVILEGED` can deploy, `BASIC` is read-only. To make an account read-only:

- **New connection:** on the AWS page that **Open AWS CloudFormation** opens, change **StacktapeConnectionMode** to `BASIC` before you choose **Create stack**.
- **Existing connection:** in the AWS CloudFormation console, in `eu-west-1`, update the stack `stacktape-<connection ID>`, keep its current template and set **StacktapeConnectionMode** to `BASIC`.

The **Status** column of the AWS accounts page then shows **Read-only** next to **Connected**, and in IAM the role has `ReadOnlyAccess` and the reporting policy, nothing else. An Owner or Admin can switch it back with **Allow deploys**.

Deploy access is administrator access because a stack can contain almost any AWS service: functions, containers, databases, networking, IAM roles for your workloads and more. A policy limited to some services would fail on the next resource you add. Your workloads don't get these permissions: each one runs with its own role that allows only what its config declares.

## Who can use the role

The role's trust policy names Stacktape's AWS account. Inside Stacktape, the Console decides who may use the account:

- Owners and Admins reach every connected account.
- Developers and Viewers reach only the AWS accounts chosen for them on the Members page. See [Team and access control](/stacktape-console/team-and-access-control#project-and-aws-account-access).
- Only Owners and Admins can connect, update or disconnect an account.

When a person causes an AWS call, Stacktape names them in it: the source identity `stp-<user ID>` and a role session name that starts with `stp-`. Background work uses session names that start with `stacktape-`. The Console's [audit log](/stacktape-console/audit-log) turns these into names. A connection created before source identities were supported shows an update link on the AWS accounts page.

## Supported regions

The role works in every region, but Stacktape deploys only to the regions it supports. The allowed values of [`--region`](/cli/deploy#option-deploy-region) list them. An AWS service can still be missing in a supported region, and an SCP or organization guardrail can block a region.

## Restrict what Stacktape can do

**Service control policies.** An SCP in AWS Organizations limits every role in the account, Stacktape's included, whatever its own policy allows. Use it to block regions, protect resources with a tag, or deny actions you never want. A deploy that an SCP blocks fails with `AccessDenied`; the CloudFormation event names the action.

**Separate accounts.** The usual setup is one AWS account for production with stricter SCPs and one for development and previews. Each account has its own connection and its own role, and members can get access to one without the other.

**Read-only.** Keep an account read-only when you only want logs, metrics and costs in the Console, for example an account another tool deploys.

**Guardrails.** Console [guardrails](/guardrails/overview) refuse deploys that break your rules, such as oversized instances or a region you don't use, before anything reaches AWS.

## Revoke access

1. Open **Configuration → AWS accounts** and choose **Disconnect account** in the account's menu. The Console blocks this while [Git deployments](/ci-cd-and-gitops/gitops-with-console) target the account and lists the projects to change first.
2. Delete the connection stack in the AWS CloudFormation console, in `eu-west-1`. That removes the role and the cost report bucket.

Deleting only the stack leaves the account in the Console as **No access**. Your deployed stacks are separate CloudFormation stacks and keep running either way; manage or delete them with the CLI and your own credentials.

## Audit Stacktape's activity

Filter AWS CloudTrail by the role's ARN to see each call Stacktape made. The `stp-` source identity and session names say which person caused it, and the Console's [audit log](/stacktape-console/audit-log) shows the same events with names.
