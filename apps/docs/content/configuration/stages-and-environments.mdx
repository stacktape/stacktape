# Stages and environments

A stage is a named deployment of your project, such as `dev`, `staging` or `production`. Each stage is a separate
CloudFormation stack with its own application resources: databases, functions, queues and buckets. Non-production
stages in the same AWS account and region usually share one VPC; see
[Shared network for non-production stages](/configuration/connecting-resources#shared-network-for-non-production-stages).

## Why stages exist

Most teams need at least two copies of their infrastructure: one to develop against and one for production. With
stages you keep one `stacktape.ts` and branch on `stage` where sizing, secrets or features differ. For example, `dev`
runs one small container and `production` runs two larger ones with a multi-AZ database.

A deploy to `dev` doesn't touch production's databases, functions or storage. A common CI setup deploys `main` to
`production` and each feature branch to a short-lived stage.

## How stages work

### Stack naming

Stacktape derives the CloudFormation stack name from your project name and stage:

```
{projectName}-{stage}
```

A project named `my-api` deployed to stage `dev` creates a stack called `my-api-dev`. The same project deployed to
`production` creates `my-api-production`.

### Stage name constraints

A stage name has at least 2 characters and contains only lowercase letters, numbers and hyphens. The project name, a hyphen and the stage form the CloudFormation stack name, which can have at most 128 characters. Examples of valid stage names: `dev`, `staging`, `production`, `pr-42`, `dev-john`.

<Warning>
  Keep stage names short. The combined project name + stage forms the CloudFormation stack name and the names of AWS
  resources. When a resource name would be longer than AWS allows, Stacktape shortens it and adds a short hash. The
  stack works the same, but these names are harder to recognize in the AWS console.
</Warning>

### Deploying a stage

Pass the `--stage` flag to [`stacktape deploy`](/cli/deploy) to target a specific stage.

Deploy a development stage:

```bash
stacktape deploy --stage dev --region eu-west-1
```

Deploy production:

```bash
stacktape deploy --stage production --region eu-west-1
```

Deleting a stage removes only that stage's resources.

## Production and non-production stages

Stacktape treats production stages differently in a few places: production error groups enter the incident queue, deleting a production stack needs a stronger Console permission, and [security findings](/cli/validate#security-findings-by-stage-purpose) are rated for production. A database open to the internet, for example, is `HIGH` in production and `LOW` in a dev stage.

A stage is production when `stackConfig.stageType` is `production`. Without that setting, the type you chose when you created the stage in the Stacktape Console decides. Otherwise Stacktape decides from the stage name: `prod`, `production`, `prd` and `live`, alone, as a segment (`prod-eu`, `client-a-prod`) or followed by a number (`prod2`), count as production, and names with a rehearsal marker (`pre-prod`, `prod-test`, `staging-live`) do not. `deploy` reads the Console's type; a plain `validate` does not contact the Console and uses the config and the name. Set `stageType` when your production stage has another name, such as `main`:

```typescript
export default defineConfig(({ stage }) => ({
  stackConfig: { stageType: stage === 'main' ? 'production' : 'non-production' },
  resources: {
    // ...
  }
}));
```

## Stage-aware configuration

The `defineConfig` callback receives a `stage` parameter. Use standard TypeScript logic (conditionals, lookup objects, helper functions) to vary your config per stage.

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import {
  defineConfig,
  LambdaFunction,
  RelationalDatabase,
  RdsEnginePostgres,
  $Secret,
  JsBundleLambdaPackaging
} from 'stacktape';

// [!code focus-start]
export default defineConfig(({ stage }) => {
  const isProduction = stage === 'production';

  const database = new RelationalDatabase({
    engine: new RdsEnginePostgres({
      version: '16',
      primaryInstance: {
        instanceSize: isProduction ? 'db.t4g.medium' : 'db.t4g.micro',
        multiAz: isProduction
      }
    }),
    credentials: {
      masterUserPassword: $Secret('db-password-' + stage)
    }
  });

  const api = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/handler.ts'
    }),
    memory: isProduction ? 1024 : 256,
    timeout: isProduction ? 30 : 10,
    environment: {
      LOG_LEVEL: isProduction ? 'warn' : 'debug'
    },
    connectTo: [database]
  });

  return { resources: { database, api } };
});
// [!code focus-end]
`
    }
  ]}
/>

In this example, the production stage gets a larger database instance with multi-AZ redundancy, more Lambda memory, and
tighter log levels: while development stages use minimal resources to keep costs low. The `$Secret` directive
can reference a different secret name per stage, such as `db-password-dev` and `db-password-production`, when you
create separate secrets for those stages. See [Secrets](/configuration/secrets) for how to create and manage secrets.

### Config callback parameters

The `defineConfig` callback receives an object whose `stage` property is the stage name passed via `--stage`. See the [configuration files](/configuration/configuration-files) page for the full `defineConfig` API and any other properties exposed on the callback object.

### Using $Stage() in directives

When composing directive strings that need the stage value at deploy time (rather than at config-evaluation time), use
the [`$Stage()` directive](/configuration/directives). This is mainly useful in YAML configs or when building
CloudFormation-level expressions. In TypeScript configs, you can typically use the `stage` parameter directly since it's
already available as a JavaScript variable.

## Common patterns

### Multi-tier environments

Most production teams use three tiers: `dev` for daily work, `staging` for pre-release validation, and `production` for
live traffic. Use a lookup object to map each stage to its resource configuration.

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import {
  defineConfig,
  WebService,
  RelationalDatabase,
  RdsEnginePostgres,
  $Secret,
  JsBundleImagePackaging
} from 'stacktape';

// [!code focus-start]
export default defineConfig(({ stage }) => {
  const tiers: Record<
    string,
    { instanceSize: string; minInstances: number; maxInstances: number; multiAz: boolean }
  > = {
    dev: { instanceSize: 'db.t4g.micro', minInstances: 1, maxInstances: 1, multiAz: false },
    staging: { instanceSize: 'db.t4g.small', minInstances: 1, maxInstances: 3, multiAz: false },
    production: { instanceSize: 'db.t4g.medium', minInstances: 2, maxInstances: 10, multiAz: true }
  };
  const tier = tiers[stage] || tiers.dev;

  const database = new RelationalDatabase({
    engine: new RdsEnginePostgres({
      version: '16',
      primaryInstance: {
        instanceSize: tier.instanceSize,
        multiAz: tier.multiAz
      }
    }),
    credentials: {
      masterUserPassword: $Secret('db-password-' + stage)
    }
  });

  const app = new WebService({
    packaging: new JsBundleImagePackaging({ entryfilePath: './src/app.ts' }),
    resources: { cpu: 0.5, memory: 1024 },
    scaling: { minInstances: tier.minInstances, maxInstances: tier.maxInstances },
    connectTo: [database]
  });

  return { resources: { database, app } };
});
// [!code focus-end]
`
    }
  ]}
/>

The fallback `tiers[stage] || tiers.dev` means any unrecognized stage name (like `feat-xyz`) inherits the `dev`
tier. This keeps feature branch stages cheap by default.

### Feature branch stages

Create a temporary stage for any feature branch. Deploy it, test it, and delete it when the branch merges.

Deploy a feature branch stage:

```bash
stacktape deploy --stage feat-42 --region eu-west-1
```

Delete the stage after the branch merges:

```bash
stacktape delete --stage feat-42 --region eu-west-1
```

Feature branch stages are disposable by design. Each one gets its own database, its own API endpoint, and its own
resources. Keep stage names short: abbreviate branch names if needed.

### Preview environments for pull requests

Stages are a good fit for per-PR preview environments. See [Git deployments](/ci-cd-and-gitops/gitops-with-console) and [Stacks per Git branch](/ci-cd-and-gitops/stacks-per-git-branch-pattern) for setup details.

## Conditional resources

Since `defineConfig` is plain TypeScript, you can conditionally include or exclude resources per stage. This is useful
for skipping expensive resources in ephemeral stages, or adding production-only safeguards like a
[web application firewall](/resources/security/web-application-firewall).

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import {
  defineConfig,
  LambdaFunction,
  RelationalDatabase,
  RdsEnginePostgres,
  WebAppFirewall,
  $Secret,
  JsBundleLambdaPackaging
} from 'stacktape';

// [!code focus-start]
export default defineConfig(({ stage }) => {
  const resources: Record<string, any> = {};

  resources.api = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({ entryfilePath: './src/api.ts' }),
    memory: 512
  });

  if (!stage.startsWith('pr-')) {
    resources.database = new RelationalDatabase({
      engine: new RdsEnginePostgres({
        version: '16',
        primaryInstance: { instanceSize: 'db.t4g.micro' }
      }),
      credentials: {
        masterUserPassword: $Secret('db-password-' + stage)
      }
    });
  }

  if (stage === 'production') {
    resources.firewall = new WebAppFirewall({ scope: 'regional' });
  }

  return { resources };
});
// [!code focus-end]
`
    }
  ]}
/>

In this example, PR preview stages skip the database entirely (the API could use an external or shared database
instead), and only production gets a WAF. This pattern keeps preview stages fast to deploy and cheap to run.

## Stage-specific secrets

Store separate Stacktape secrets for each stage. Use
[`stacktape secret set`](/cli/secret-set) to create them, and the
[`$Secret` directive](/configuration/directives) to reference them in config.

Create separate secrets for each stage (for example, `db-password-dev` and `db-password-production`) using [`stacktape secret set`](/cli/secret-set):

```bash
stacktape secret set --region eu-west-1
```

Run the command once per secret. See the [CLI reference](/cli/secret-set) for available options.

Then reference the stage-specific secret in your config using the `stage` parameter:

## Stage-specific domains

Assign different [custom domains](/resources/networking/custom-domains) per stage to give each environment a clean URL.
Production uses the apex domain; other stages use subdomains.

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, HttpApiGateway } from 'stacktape';

// [!code focus-start]
export default defineConfig(({ stage }) => {
  const gateway = new HttpApiGateway({
    customDomains:
      stage === 'production'
        ? [{ domainName: 'api.example.com' }]
        : [{ domainName: stage + '.api.example.com' }]
  });

  return { resources: { gateway } };
});
// [!code focus-end]
`
    }
  ]}
/>

This produces:

| Stage | Domain |
|---|---|
| `production` | `api.example.com` |
| `staging` | `staging.api.example.com` |
| `dev` | `dev.api.example.com` |

Custom domains are managed separately. See [custom domains](/resources/networking/custom-domains) and [`stacktape domain add`](/cli/domain-add) for setup.

## Sharing resources across stages

To let several stages or projects share one database, put it in its own project, deploy that project once, and export what the others need. Here the `shared-infra` project runs one database for all non-production stages (stage `dev`) and one for production:

<ProjectStructure
  files={[
    {
      name: 'my-platform',
      type: 'folder',
      children: [
        {
          name: 'shared-infra',
          type: 'folder',
          children: [{ name: 'stacktape.ts', description: 'The database; exports its host and port' }]
        },
        { name: 'api', type: 'folder', children: [{ name: 'stacktape.ts', description: 'Imports the exports' }] }
      ]
    }
  ]}
/>

The shared project exports the host and port as stack outputs:

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'shared-infra/stacktape.ts',
      lang: 'typescript',
      code: `import { defineConfig, RelationalDatabase, RdsEnginePostgres, $Secret, $ResourceParam } from 'stacktape';

// [!code focus-start]
export default defineConfig({ projectName: 'shared-infra' }, ({ stage }) => {
  const database = new RelationalDatabase({
    engine: new RdsEnginePostgres({
      version: '16',
      primaryInstance: { instanceSize: 'db.t4g.micro' }
    }),
    credentials: {
      masterUserPassword: $Secret(\`shared-db-password-\${stage}\`)
    }
  });

  return {
    resources: { database },
    stackConfig: {
      outputs: [
        { name: 'DbHost', value: $ResourceParam('database', 'host'), export: true },
        { name: 'DbPort', value: $ResourceParam('database', 'port'), export: true }
      ]
    }
  };
});
// [!code focus-end]`
    }
  ]}
/>

Deploy it to the two stages the others use:

```bash
stacktape deploy --stage dev --region eu-west-1
```

```bash
stacktape deploy --stage production --region eu-west-1
```

Every stage of the `api` project then imports from one of those two stacks. `pr-42`, `staging` and `dev` all use `shared-infra-dev`:

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'api/stacktape.ts',
      lang: 'typescript',
      code: `import { defineConfig, WebService, JsBundleImagePackaging, $CfStackOutput, $Secret } from 'stacktape';

// [!code focus-start]
export default defineConfig(({ stage }) => {
  const sharedStage = stage === 'production' ? 'production' : 'dev';
  const sharedStack = \`shared-infra-\${sharedStage}\`;

  const api = new WebService({
    packaging: new JsBundleImagePackaging({ entryfilePath: './src/server.ts' }),
    resources: { cpu: 0.25, memory: 512 },
    environment: {
      DB_HOST: $CfStackOutput(sharedStack, 'DbHost'),
      DB_PORT: $CfStackOutput(sharedStack, 'DbPort')
    },
    secrets: [{ name: 'DB_PASSWORD', valueFrom: $Secret(\`shared-db-password-\${sharedStage}\`) }]
  });

  return { resources: { api } };
});
// [!code focus-end]`
    }
  ]}
/>

- Export only values that are not secret. The password stays in Secrets Manager and reaches the container through `secrets`.
- `$CfStackOutput` makes CloudFormation import the export. While any stack imports it, the shared stack cannot remove that output or be deleted; delete or update the importing stacks first. `$StackOutput` reads the value once at deploy time and creates no such link.
- `connectTo` does not work across stacks, so it grants nothing here. This example works because the database's default `accessibilityMode` is `internet`, protected by its password. For a database reachable only inside a VPC, both projects must run in a network that can reach it; see [Connecting resources](/configuration/connecting-resources#can-i-connect-to-resources-in-a-different-stack).

## Setting defaults

If you always deploy to the same stage and region during development, use [`stacktape defaults set`](/cli/defaults-configure) to set default values for stage and region. See the [CLI reference](/cli/defaults-configure) for details.

```bash
stacktape defaults set
```

Once configured, you can deploy without passing `--stage` and `--region`:

```bash
stacktape deploy
```

Override the defaults when deploying to a different stage:

```bash
stacktape deploy --stage production --region us-east-1
```

## Managing deployed stages

### Listing stacks

Use [`stacktape stack list`](/cli/info-stacks) to list deployed stacks in a region. See the [CLI reference](/cli/info-stacks) for available options.

```bash
stacktape stack list --region eu-west-1
```

### Deleting a stage

Use [`stacktape delete`](/cli/delete) to delete a stage's stack.

```bash
stacktape delete --stage feat-42 --region eu-west-1
```

Deletion removes the stage's CloudFormation stack. Other stages remain completely unaffected.

A stage that [dev mode](/local-development/dev-mode-overview) created stays a dev stack after dev mode stops, and `stacktape deploy` refuses it. Use a separate stage name for dev mode (for example `local`), or delete the dev stack with `stacktape delete --stage <stage>` before deploying that stage.

## Best practices

**Use consistent stage names.** Pick a naming convention (`dev`, `staging`, `production`) and stick to it across all
projects. Consistent names simplify CI/CD pipelines and make `$Secret('db-password-' + stage)` patterns predictable.

**Keep dev stages minimal.** Use the smallest instance sizes and lowest scaling in development. The multi-tier lookup
pattern shown above makes this automatic and keeps development costs low without manual intervention.

**Make staging mirror production.** The whole point of a staging stage is to catch issues before production. Use the
same instance types, same scaling ranges, and same configuration: just with test data and lower traffic.

**Separate secrets per stage.** Never reuse production credentials in development. Stage-interpolated secret names
(`db-password-dev`, `db-password-production`) enforce this by convention.

**Delete ephemeral stages promptly.** Feature branch and PR preview stages accumulate if not cleaned up. See
[Git deployments](/ci-cd-and-gitops/gitops-with-console) and [Stacks per Git branch](/ci-cd-and-gitops/stacks-per-git-branch-pattern) for setting up preview-stage workflows, or manually run
[`stacktape delete`](/cli/delete).

**Add safeguards in production.** Enable multi-AZ for databases, add a
[web application firewall](/resources/security/web-application-firewall), configure
[alarms](/observability/alarms), and set [budgets](/managing-costs/budgets). Use conditional resource inclusion
to add these only in production.

## FAQ

### How do I access the stage name in my config?

The `defineConfig` callback receives an object with a `stage` property. Use standard TypeScript logic to branch on the stage value: ternary operators, lookup objects, or if statements all work. In directive strings that need the stage at CloudFormation deploy time, use the [`$Stage()` directive](/configuration/directives).

### Can I include resources only in certain stages?

Yes. Since `defineConfig` returns a plain JavaScript object, you can conditionally add keys to the `resources` object using `if` statements or any other control flow. Resources not included in the returned object are simply not created for that stage. This is commonly used to skip databases in preview stages or add WAFs only in production.

### Are stages fully isolated from each other?

Their application resources are separate, and deploying or deleting one stage does not touch the others. Two things are shared:

- **The network.** Non-production stages of an account and region usually run in one VPC, the [shared network](/configuration/connecting-resources#shared-network-for-non-production-stages). Each stage has its own security groups, so one stage cannot reach another stage's databases by private IP. Where a stage runs is decided on its first deploy and doesn't change later, even when the stage becomes production.
- **The AWS account.** Anyone with deploy credentials for the account can reach every stage in it. To keep production away from people who deploy previews, deploy it to its own AWS account.

### What happens when I deploy to an existing stage?

Deploying to an existing stage updates that stage's CloudFormation stack rather than creating a new one. CloudFormation computes the diff between the current and desired state and applies only the changes needed. Deleting a stage removes only that stage's stack: other stages are unaffected.

### Can different stages use different AWS regions?

Yes. The region is a separate parameter from the stage, so you can deploy `dev` to `eu-west-1` and `production` to `us-east-1`. The stack name is derived from `{projectName}-{stage}`, and region-scoped resources (like secrets and ACM certificates) must exist in the target region. Create stage-appropriate secrets in each region you deploy to.

### How do I keep development costs low across stages?

Vary resource sizing by stage. Branch on the `stage` parameter to give dev and preview stages the smallest instance sizes and lowest scaling, while production gets larger instances and multi-AZ: the multi-tier lookup pattern shown above makes this automatic. You can also conditionally skip expensive resources (like a database) in ephemeral `pr-*` stages, or have several services in the same stage share one database via the [`$CfStackOutput` directive](/configuration/directives).
