# Going to production

Your app is deployed. Before real users arrive, add alarms, database backups, a budget, your own domain, gradual rollouts and, for a team, guardrails. Each section says what to configure and links to the full guide.

Most of it is configuration that works with the CLI alone. Budgets and guardrails are [Console](/getting-started/add-the-console) features; each section says so, and what to use without the Console.

Deploy production as its own stage, for example `--stage production`, ideally in a separate AWS account from development.

## Alarms

Stacktape alarms monitor CloudWatch metrics and notify your team when thresholds are breached. Define alarms on individual resources in your stack config and deploy to apply them. They are CloudWatch alarms in your AWS account. The [Stacktape Console](/stacktape-console/console-overview) also shows their state and history.

Alarm triggers cover the most critical failure modes: Lambda error rate and duration, database CPU/memory/storage/connections/latency, HTTP API Gateway error rate and latency, Application Load Balancer error rate and unhealthy targets, and SQS received-message count and not-empty alarms. Each alarm supports configurable evaluation windows — period length, how many periods to evaluate, and how many must breach before firing.

Without `notificationChannels`, alarms change state in CloudWatch but nobody gets paged. Always route alarms to at least one notification channel. Stacktape supports five channel types: Slack, Microsoft Teams, Discord, email, and custom webhooks.

<CodeBlock

  tabs={[

      label: 'TypeScript',

      code: `import { defineConfig, LambdaFunction, JsBundleLambdaPackaging } from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const api = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/api.ts'
    }),
    memory: 1024,
    timeout: 30,
    alarms: [
      {
        trigger: {
          type: 'lambda-error-rate',
          properties: { thresholdPercent: 5 }
        },
        evaluation: {
          period: 60,
          evaluationPeriods: 3,
          breachedPeriods: 2
        },
        notificationChannels: [
          {
            type: 'email',
            properties: {
              sender: 'alerts@example.com',
              recipient: 'oncall@example.com'
            }
          }
        ]
      }
    ]
  });

  return { resources: { api } };
});
// [!code focus-end]`
    }
  ]}
/>

This alarm fires when more than 5% of invocations fail in at least 2 out of 3 consecutive 60-second windows — filtering out isolated spikes while catching sustained problems. The `evaluation` block controls this: `period` sets each window to 60 seconds, `evaluationPeriods: 3` looks at the last three windows, and `breachedPeriods: 2` requires at least two to breach before firing. The email notification target ensures your on-call team is alerted immediately.

For production, most teams use Slack (`type: 'slack'` with `conversationId` and `accessToken`) or a custom webhook. See [Alarms](/observability/alarms) for all trigger types, notification channel configuration, and migration of legacy Console rules.

## Database backups

AWS takes a daily backup of a [relational database](/resources/databases/relational-database). `automatedBackupRetentionDays` sets how many days are kept: `1` by default, up to `35`. For production, keep at least `7`, so you can still recover from a problem you find days later. Set `deletionProtection: true` so a deploy or a delete can't remove the database. A database added by `stacktape init` has deletion protection on, and **Keep recovery copies** on the Review step sets 7 days of backups. See [Backups and maintenance](/resources/databases/relational-database#backups-and-maintenance).

## Budgets

Budgets catch surprise AWS bills. In the [Stacktape Console](/getting-started/add-the-console), a budget sets a monthly spending limit for one connected AWS account and alerts your [alert channels](/observability/alert-channels) when the account's spend crosses percentages of it (80% and 100% by default). Forecast alerts, on by default, also warn you when AWS forecasts that the month's spend will cross a percentage.

A budget watches the whole AWS account. It cannot filter by project or stage. If you want separate limits for production and development, run them in separate AWS accounts. See [Budgets](/managing-costs/budgets) for setup details.

Without the Console, create a budget in the AWS console under **Billing and Cost Management** → **Budgets**. It can email you when actual or forecast spend crosses a threshold.

<Tip>
Create a budget for every AWS account that runs production stages. Even a generous limit catches mistakes such as a runaway Lambda loop or an oversized database instance before they become expensive. Set the limit to your expected monthly bill and keep the default 80% and 100% alerts.
</Tip>

## Custom domains

Stacktape [web services](/resources/compute/web-service) support custom domains through the `customDomains` property. When the domain's DNS is in Route 53 in your AWS account, Stacktape creates the DNS records and the TLS certificate for you. The example below shows the most common case, a web service API. Other public resources are covered in the [Custom domains](/resources/networking/custom-domains) guide.

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, WebService, JsBundleImagePackaging } from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const api = new WebService({
    packaging: new JsBundleImagePackaging({
      entryfilePath: './src/server.ts'
    }),
    resources: { cpu: 0.25, memory: 512 },
    environment: { NODE_ENV: 'production' },
    customDomains: [{ domainName: 'api.example.com' }]
  });

  return { resources: { api } };
});
// [!code focus-end]`
    }
  ]}
/>

There are two ways to set up the domain:

- **DNS in Route 53.** Run [`stacktape domain add`](/cli/domain-add) for a domain you already own. It checks the domain, can move its DNS to a Route 53 hosted zone in your account and requests the TLS certificates. After that, `customDomains` is all a resource needs.
- **DNS at your current provider**, such as Cloudflare. Request a certificate in AWS Certificate Manager, set `customCertificateArn` and `disableDnsRecordCreation: true`, deploy, and add a CNAME record at your provider. See [External DNS](/resources/networking/custom-domains#external-dns).

Custom domains add no Stacktape cost. In AWS, a Route 53 hosted zone and its DNS queries cost a little each month, and the certificates are free.

## Gradual deployments

Instead of switching all traffic to a new version instantly, gradual deployments shift traffic incrementally — catching regressions before they affect all users. Stacktape supports canary and linear strategies for [Lambda functions](/resources/compute/lambda-function) and [web services](/resources/compute/web-service) (and other container workloads — see [Gradual deployments](/deployment-and-lifecycle/gradual-deployments) for the full list).

**Lambda functions** support nine deployment strategies. Canary strategies (`Canary10Percent5Minutes`, `Canary10Percent10Minutes`, `Canary10Percent15Minutes`, `Canary10Percent30Minutes`) send 10% of traffic to the new version first, then shift the rest after the specified wait period. Linear strategies (`Linear10PercentEvery1Minute`, `Linear10PercentEvery2Minutes`, `Linear10PercentEvery3Minutes`, `Linear10PercentEvery10Minutes`) shift 10% of traffic at regular intervals until complete. `AllAtOnce` provides an instant switch with no gradual rollout.

Lambda deployments also support optional `beforeAllowTrafficFunction` and `afterTrafficShiftFunction` hooks — references to Lambda functions in your config that run smoke tests before traffic begins shifting and validation after all traffic has moved. If the `beforeAllowTrafficFunction` hook signals failure, the deployment rolls back.

**Web services** and other container workloads expose gradual deployments through the `deployment` property, which requires `application-load-balancer` load balancing. Container workloads support five strategies: `Canary10Percent5Minutes`, `Canary10Percent15Minutes`, `Linear10PercentEvery1Minutes`, `Linear10PercentEvery3Minutes`, and `AllAtOnce`. Container deployments also support `beforeAllowTrafficFunction` and `afterTrafficShiftFunction` hooks. See [Gradual deployments](/deployment-and-lifecycle/gradual-deployments) for rollback behavior and hook configuration.

### Lambda function example

<CodeBlock
  intellisense
  tabs={[
    {
      label: 'TypeScript',
      lang: 'typescript',
      code: `import { defineConfig, LambdaFunction, JsBundleLambdaPackaging } from 'stacktape';

// [!code focus-start]
export default defineConfig(() => {
  const api = new LambdaFunction({
    packaging: new JsBundleLambdaPackaging({
      entryfilePath: './src/api.ts'
    }),
    deployment: {
      strategy: 'Canary10Percent5Minutes'
    }
  });

  return { resources: { api } };
});
// [!code focus-end]`
    }
  ]}
/>

`Canary10Percent5Minutes` sends 10% of traffic to the new version for 5 minutes before shifting the rest. This is a good starting point for most production APIs — it validates with real traffic on a small slice before committing. If your service handles high traffic and you want more gradual rollout, consider `Linear10PercentEvery3Minutes` for a 30-minute complete rollout.

Container gradual deployments require `loadBalancing` set to `application-load-balancer` — the default `http-api-gateway` does not support traffic shifting. The ALB adds a flat base cost (~$18/month), but enables gradual rollouts, WebSocket support, and top-level firewalls. See [Gradual deployments](/deployment-and-lifecycle/gradual-deployments) for strategy comparisons.

## Multi-region deployments

Deploy the same stack to multiple AWS regions for lower latency or regional compliance. Each region gets its own independent stage — deploy with `--region eu-west-1` and `--region us-east-1` as separate commands or CI pipelines. Stacktape does not automatically replicate data between regions; you handle cross-region data strategy (DynamoDB global tables, Aurora Global Database, or application-level replication).

Multi-region adds operational complexity and cost — you manage separate deployments, cross-region data consistency, and region-specific monitoring. Use it when you have users on multiple continents and latency matters, or when regulations require data residency in specific regions. For most apps, a single region with a [CDN](/resources/networking/cdn) provides good global performance at lower cost. See [Multi-region deployments](/deployment-and-lifecycle/multi-region-deployments) for patterns and tradeoffs.

## Guardrails

Guardrails are a [Console](/getting-started/add-the-console) feature. They define organization-wide policy rules that restrict what deployments can do — which stages and regions are allowed, what resource types and sizes are permitted, and which security settings are required. They prevent teams from deploying configurations that violate your standards.

Available guardrail types cover four categories:

| Category | Guardrail types |
|----------|----------------|
| **Deployment** | Stage restriction, region restriction, command restriction, resource type restriction, resource count limit |
| **Security** | Require VPC-only databases, require WAF on application load balancers, require custom domains on web services and hosting buckets |
| **Data protection** | Require deletion protection on relational databases, require dead-letter queues on SQS queues |
| **Resource limits** | Function memory limit, function timeout limit, container CPU/memory limit, database engine restriction, database instance size restriction |

Guardrails are most valuable once your team has more than one person deploying, or when you run both production and development stages and want to enforce stricter rules on production. For solo developers or early-stage projects, you can skip guardrails and revisit when your team or compliance requirements grow. See [Guardrails](/guardrails/overview) for configuration details and per-type documentation.

## Verify before go-live

Before sending real traffic, run through these concrete checks:

1. **Confirm alarms notify correctly.** Trigger a test error in your function or service and verify the notification reaches your on-call channel. An alarm without `notificationChannels` fires silently in CloudWatch — check that every production alarm has at least one target configured. Use [`stacktape logs`](/cli/logs) to confirm CloudWatch is receiving log data.

2. **Check database backups.** Confirm `deletionProtection: true` and at least 7 days of `automatedBackupRetentionDays` on every production database. In the AWS console, **RDS** → your database → **Maintenance & backups** shows the latest backup.

3. **Set a budget.** Create a budget for your production AWS account with a monthly limit matching your expected spend: under **Budgets** in the Stacktape Console, or in AWS Budgets without it. Keep alerts at 80% and 100% of the limit, and turn on forecast alerts so you hear about a trend before it reaches the limit.

4. **Verify your custom domain resolves.** Open your custom domain in a browser and confirm the TLS certificate is valid (lock icon, no warnings). With DNS in Route 53, Stacktape creates the records. With external DNS, check that the CNAME record points to the AWS hostname.

5. **Test a gradual deployment.** Deploy a small change and watch the CLI output, or the deployment in the Console. Confirm that traffic shifts according to your chosen strategy, and use [`stacktape logs`](/cli/logs) to check that the new version handles requests.

6. **Review guardrails (Console).** Confirm deletion protection is required for production databases, VPC-only access is enforced where needed, and resource limits match your team's standards. See [Guardrails](/guardrails/overview) for the full list of policy rules.
