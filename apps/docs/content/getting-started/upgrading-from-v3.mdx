# Upgrading from v3

Stacktape v4 makes deliberate breaking changes. v4 does not accept the old names, so update your configuration before deploying with v4. This page covers packaging, removed resource parameters and what the first v4 deployment changes in an existing stack.

## Deployed stacks

Deploying a v4 configuration over a stack created by v3 is an ordinary stack update. Databases, buckets, DynamoDB tables, Redis caches, EFS file systems, user pools, Kinesis streams and SQS queues keep their CloudFormation logical IDs and physical names, so they are neither replaced nor deleted. Default domains keep their names as well. Stacktape checks this before every deployment: the change plan printed by `stacktape deploy` lists every resource it would replace or delete, and it stops for confirmation when one of them holds data.

The first v4 deployment adds a log subscription filter to every function and container log group for issue detection. On stacks without databases, load balancers or private service discovery, it also deletes Stacktape's internal tagging schedule (an EventBridge rule and its Lambda permission), which had nothing to tag.

On stacks with a CDN, it deletes Stacktape's origin-response Lambda@Edge function unless a bucket sets custom metadata headers, the only case that uses it. It also deletes the origin-request Lambda@Edge function unless a bucket cache behaviour uses URL normalization or SPA routing without a custom origin-request handler. API Gateway, load balancer, Lambda URL and custom HTTP origins do not use that helper. When no edge function remains, its internal artifact bucket is removed too. CloudFormation updates distributions before deleting a helper they previously referenced. AWS may retain detached Lambda@Edge replicas for a few hours; this does not fail the update. After AWS releases the replicas, delete any retained function in `us-east-1` with `aws lambda delete-function --profile <profile> --region us-east-1 --function-name <name>`.

Batch jobs now run on Amazon Linux 2023 instances, because AWS Batch stopped creating compute environments with its Amazon Linux 2 images on 30 June 2026. A compute environment last deployed by v3.0.10 or later keeps Amazon Linux 2: changing the image would make CloudFormation replace the environment and could interrupt jobs running on it. AWS keeps such environments running but no longer patches their image. An older environment, or one that a later change replaces anyway (such as a change to the stack's `tags`), moves to Amazon Linux 2023. CloudFormation then deletes the old environment, which can interrupt jobs still running on it, so deploy such a change when no jobs run; the change plan lists the compute environment as replaced. Amazon Linux 2023 requires IMDSv2 and uses cgroup v2; see [compute resources](/resources/compute/batch-job#compute-resources). The first v4 deployment also gives each batch job an execution role with `AmazonECSTaskExecutionRolePolicy`, which the ECS agent uses to pull the job's image from ECR, write its logs and read its secrets. The job's own role is unchanged.

Existing organization-wide Console alarm rules remain as legacy rules. The Console no longer creates or edits alarm rules; use `stacktape alarm export` to [move them into stack configuration](/observability/alarms#migrating-legacy-console-alarm-rules).

Container services without gradual deployments shut down more gracefully in v4. The default container `stopTimeout` is 30 seconds instead of 2, and a load balancer gives an old container 30 seconds instead of 5 to finish its requests. The first v4 deployment therefore registers a new task definition and replaces the running containers, as a code change would. Set `stopTimeout: 2` on a container to keep the v3 shutdown window.

A container service whose `minInstances` equals `maxInstances` (the default is 1 and 1) no longer gets CPU and memory scaling policies, because they could never change its instance count. Services whose `overrides` change the scalable target or a scaling policy keep both policies. The first v4 deployment deletes both policies and their CloudWatch alarms. The service keeps its scalable target and its instance count.

Code-only deployments of web services behind the default HTTP API finish once the new tasks are `RUNNING` and API Gateway can discover them, plus a 4-second routing allowance. Old tasks drain in the background. No health check is added by default, so this does not confirm that the new application works. Add an `internalHealthCheck` for application failure detection and automatic rollback. HTTP API tasks also gain a managed drain container, which waits 35 seconds before ECS signals the application so cached routes can expire. This uses one of ECS's 10 container slots and has a 16 MiB memory limit. The protection applies once those task definitions are running; the first rollout still retires the previous unprotected tasks. Keep an application shutdown delay or use a maintenance window for that transition. Services with an `internalHealthCheck`, and ALB/NLB services, keep their existing health-based completion checks. Code-only deploy timing stays the same. Full CloudFormation deployments, scale-in and deletion take about 36 seconds longer per task stop; tasks can stop in parallel. The 35-second delay can be raised through task definition overrides, with a matching increase to the helper’s stop timeout. The helper is non-essential and pulls a digest-pinned image from the stack’s private ECR; the CLI copies both amd64 and arm64 images there once without Docker. The privileged Console connection role already covers this copy. Restricted deployer roles need `ecr:BatchGetImage`, `ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload` and `ecr:PutImage` on the stack’s deployment repository, even when all application images are prebuilt. Upgrade every team and Console runner CLI before adopting the helper: older CLIs can delete its cached images during retention. See [web-service health checks](/resources/compute/web-service#health-checks).

## CLI command and flag names

v4 commands and flags use standard spelling: words separated by spaces, and lowercase flags with dashes. For example, `stacktape secret set my-key --region eu-west-1` replaces `stacktape secret:set --region eu-west-1 --secretName my-key`. The old spellings, such as colon commands (`info:stack`) and camelCase flags (`--projectName`), still work, so existing scripts and CI jobs keep running. Run `stacktape help <command>` to see the current names.

## Error tracking names

Use `error list`, `error ignore`, `error resolve`, and `error reopen` in place of the `issues:*` CLI commands. The `issues:*` commands still work, so existing scripts, automation and MCP command requests keep running. Replace `deploymentConfig.issues` with `deploymentConfig.errorTracking` in YAML and TypeScript configs; the old config name is rejected. Issue IDs and status values are unchanged. See [Error tracking](/observability/error-tracking) for capture settings and triage commands.

## Failed deployments keep what they created

v3 rolled a failed deployment back: a failed update returned the stack to its previous state, and a failed first deployment deleted the stack, including a database that had already taken minutes to create. In v4, a failed deployment keeps every resource it created or updated, unless it replaced existing resources: CloudFormation can only replace resources in a deployment it may roll back. The stack stays in `CREATE_FAILED` or `UPDATE_FAILED`, and the next `stacktape deploy` continues from the failure. To undo a failed update, run `stacktape stack recover`; to remove a failed first deployment, run `stacktape delete`. See [when a deployment fails](/deployment-and-lifecycle/deploying-stacks#when-a-deployment-fails).

- Replace `deploymentConfig.disableAutoRollback: true` by deleting it; this is now the default. The old name is rejected.
- To keep the v3 behaviour, set `deploymentConfig.autoRollback: true`, or pass `--auto-rollback` to one deployment. Stacks with `triggerRollbackOnAlarms` or `monitoringTimeAfterDeploymentInMinutes` keep rolling back automatically without a change.
- Remove `--no-auto-rollback` (`--disableAutoRollback`, `--dar`) from scripts and CI jobs. The flag no longer exists.

## Security findings in agent output

In the `--agent` result of `validate` and `deploy`, one `security` object replaces the `securityFindings` and `securityExposure` fields that `4.0.0-preview.10` returned: read `security.findings` and `security.exposure` instead. See [security findings by stage purpose](/cli/validate#security-findings-by-stage-purpose).

## Target AWS account

v3 stack commands ignored `--profile` and `AWS_PROFILE` for accounts connected with Stacktape-managed access. They deployed to `--aws-account`, the saved default, or the organization's only connected account. In v4, when `--aws-account` is not set, `--profile`, `AWS_PROFILE` or AWS keys in the environment choose the connected account they belong to. If they belong to an account that is not connected, the command stops before changing anything.

Check scripts and CI jobs that set an AWS profile or AWS keys for a different account than the one they deploy to. Pass `--aws-account <name>` in them, or remove the AWS settings. See [Choosing the account for a CLI command](/stacktape-console/connecting-your-aws-account#choosing-the-account-for-a-cli-command).

## Redis caches

`type: redis-cluster` is now `type: redis`, and the node settings (`instanceSize`, replicas, sharding, `port`, `logging`) moved under `engine.properties`. To keep a deployed cache unchanged, use `engine.type: redis` and set `version` to the version it runs: the former `engineVersion`, or `6.2` if it was not set. The CLI rejects `redis-cluster` and prints this replacement for your settings. TypeScript configs replace `RedisCluster` with `Redis`.

The cache keeps its endpoint and data. New caches use Valkey (`engine.type: valkey` or `valkey-serverless`); to move an existing cache to Valkey, change `engine.type` to `valkey`. See [Redis](/resources/databases/redis#migrating-from-redis-cluster).

## Removed resource parameters

The `MultiContainerWorkload` class no longer has a `logGroupArn` property, and `$ResourceParam('<workload>', 'logGroupArn')` is rejected. Stacktape never published this parameter, so a v3 configuration using it could not deploy.

A multi-container workload has one log group per container. To reference one, use [`$CfResourceParam`](/configuration/directives) with the log group's CloudFormation logical ID: the workload name and the container name in PascalCase, followed by `LogGroup`. For the `app` container of a workload named `orders`, use `$CfResourceParam('OrdersAppLogGroup', 'Arn')`. A container with `logging.disabled` has no log group. Run [`stacktape synth`](/cli/synth) to check the logical IDs in the generated template.

## User auth pool token lifetimes

v3 sent `accessTokenValiditySeconds` and `idTokenValiditySeconds` to Cognito without a unit, so Cognito read them in hours and accepted only 1 to 24. v4 sends them in seconds. A value from 1 to 24 keeps its meaning in hours, and the CLI warns you to write it in seconds: replace `accessTokenValiditySeconds: 1` with `accessTokenValiditySeconds: 3600`. Unset lifetimes stay at 1 hour, and deploying updates the user pool client in place. See [token lifetimes](/resources/security/user-auth-pool#token-lifetimes).

The CLI does not warn about `overrides`. If you set `AccessTokenValidity` or `IdTokenValidity` on the user pool client through `overrides`, the value is now read in seconds, so a value that meant hours fails to deploy. Set the matching unit in the same override, or replace the override with `accessTokenValiditySeconds` or `idTokenValiditySeconds`. For a pool named `auth`:

```yaml
overrides:
  AuthUserPoolClient:
    AccessTokenValidity: 2
    TokenValidityUnits:
      AccessToken: hours
```

## Packaging

v4 replaces the v3 packaging types with a smaller set:

| v3 type | v4 type | v4 class |
|---|---|---|
| `stacktape-lambda-buildpack`, JavaScript or TypeScript entry file | `js-bundle` | `JsBundleLambdaPackaging` |
| `stacktape-lambda-buildpack`, Python, Java, Go, Ruby or .NET entry file | `buildpack` | `BuildpackLambdaPackaging` |
| `stacktape-image-buildpack`, JavaScript or TypeScript entry file | `js-bundle` | `JsBundleImagePackaging` |
| `stacktape-image-buildpack`, other languages | `buildpack` | `BuildpackImagePackaging` |
| `nixpacks` | `buildpack` | `BuildpackImagePackaging` |
| `external-buildpack` | `buildpack` or `dockerfile` | `BuildpackImagePackaging` or `DockerfilePackaging` |
| `custom-dockerfile` | `dockerfile` | `DockerfilePackaging` |
| `custom-artifact` | `custom-artifact` (unchanged) | `CustomArtifactLambdaPackaging` |
| `prebuilt-image` | `prebuilt-image` (unchanged) | `PrebuiltImagePackaging` |

In TypeScript configurations, rename the classes in both the `new ...Packaging(...)` calls and the `import` list.

### JavaScript and TypeScript Lambda functions

Rename the type to `js-bundle` and move the options from `languageSpecificConfig` up one level.

Before:

```yaml
resources:
  api:
    type: function
    properties:
      packaging:
        type: stacktape-lambda-buildpack
        properties:
          entryfilePath: ./src/api.ts
          languageSpecificConfig:
            nodeVersion: 22
            outputModuleFormat: esm
```

After:

```yaml
resources:
  api:
    type: function
    properties:
      packaging:
        type: js-bundle
        properties:
          entryfilePath: ./src/api.ts
          nodeVersion: 22
          outputModuleFormat: esm
```

See [JS Bundle for Lambda](/packaging/function/js-bundle).

### Python, Java, Go, Ruby and .NET Lambda functions

Rename the type to `buildpack`. Rename `languageSpecificConfig` to `python`, `java` or `dotnet`, depending on the language. Delete the version fields and set the function's `runtime` instead. Go and Ruby have no options, so delete their `languageSpecificConfig`.

Before:

```yaml
resources:
  processor:
    type: function
    properties:
      packaging:
        type: stacktape-lambda-buildpack
        properties:
          entryfilePath: ./src/process.py
          languageSpecificConfig:
            pythonVersion: 3.12
            packageManagerFile: ./pyproject.toml
            minify: false
```

After:

```yaml
resources:
  processor:
    type: function
    properties:
      runtime: python3.12
      packaging:
        type: buildpack
        properties:
          entryfilePath: ./src/process.py
          python:
            packageManagerFile: ./pyproject.toml
```

v3 ignored the runtime when it built a function: without a version field, it built for Python 3.12, Java 11, Ruby 3.3 or .NET 8. v4 builds for the function's runtime. A function without `runtime` keeps `python3.13` or `dotnet10`, as in v3. Java moves from `java21` to `java25` and Ruby from `ruby3.3` to `ruby4.0`; set `runtime` to keep the v3 one.

See [Buildpack for Lambda](/packaging/function/buildpack).

### Rust Lambda functions

v3 had no Rust support, so Rust functions used `custom-artifact` with a hook that ran cargo-lambda. In v4, delete the hook and use `buildpack`.

Before:

```yaml
hooks:
  beforeDeploy:
    - scriptName: buildRust
scripts:
  buildRust:
    type: local-script
    properties:
      executeCommand: cargo lambda build --release --output-format zip
resources:
  resizer:
    type: function
    properties:
      runtime: provided.al2023
      packaging:
        type: custom-artifact
        properties:
          packagePath: ./target/lambda/resizer/bootstrap.zip
```

After:

```yaml
resources:
  resizer:
    type: function
    properties:
      runtime: provided.al2023
      packaging:
        type: buildpack
        properties:
          entryfilePath: src/main.rs
```

### JavaScript and TypeScript container services

Rename the type to `js-bundle` and move the options from `languageSpecificConfig` up one level. `requiresGlibcBinaries` and `customDockerBuildCommands` stay where they are.

Before:

```yaml
resources:
  api:
    type: web-service
    properties:
      packaging:
        type: stacktape-image-buildpack
        properties:
          entryfilePath: ./src/server.ts
          requiresGlibcBinaries: true
          languageSpecificConfig:
            emitTsDecoratorMetadata: true
      resources:
        cpu: 0.25
        memory: 512
```

After:

```yaml
resources:
  api:
    type: web-service
    properties:
      packaging:
        type: js-bundle
        properties:
          entryfilePath: ./src/server.ts
          requiresGlibcBinaries: true
          emitTsDecoratorMetadata: true
      resources:
        cpu: 0.25
        memory: 512
```

The v4 image installs nothing beside the runtime by default. v3 images ran `tini` and shipped `curl` and `openssl`:

- ECS and AWS Batch now start the init process (`initProcessEnabled`), so stop signals still reach your server.
- `curl` is installed only when the container's `internalHealthCheck` command calls it. If a script in the image calls `curl`, or your code runs the `openssl` command, add it with `customDockerBuildCommands`, for example `apk add --no-cache curl`.
- The OpenSSL libraries that Prisma loads are still in the image. When your code, or a package installed beside the bundle, uses Prisma, the Alpine image also gets the `openssl` command, which Prisma 5 needs to choose its query engine.

See [JS Bundle for Containers](/packaging/containers/js-bundle).

### Python and other non-JavaScript container services

Rename the type to `buildpack`. The container `buildpack` builds the whole project directory, so replace `entryfilePath` with `sourceDirectoryPath`. Replace `runAppAs` with a `startCommand` that starts the server on `$PORT`, and add the server (for example `uvicorn` or `gunicorn`) to the project's dependencies.

Before:

```yaml
resources:
  api:
    type: web-service
    properties:
      packaging:
        type: stacktape-image-buildpack
        properties:
          entryfilePath: ./app/main.py:app
          languageSpecificConfig:
            runAppAs: ASGI
            packageManagerFile: ./pyproject.toml
      resources:
        cpu: 0.5
        memory: 1024
```

After:

```yaml
resources:
  api:
    type: web-service
    properties:
      packaging:
        type: buildpack
        properties:
          sourceDirectoryPath: .
          startCommand: uvicorn app.main:app --host 0.0.0.0 --port $PORT
      resources:
        cpu: 0.5
        memory: 1024
```

For a WSGI app, use gunicorn, for example `gunicorn --bind 0.0.0.0:$PORT app.main:app`. When a FastAPI, Flask or Django project uses the conventional module layout, the start command is detected and `startCommand` can be omitted.

The v4 images are Debian-based and larger than the v3 Alpine images. See [Buildpack for Containers](/packaging/containers/buildpack).

### Nixpacks

Rename the type to `buildpack` and `startCmd` to `startCommand`. Nixpacks phases have no direct equivalent: move install and build commands to `installCommand` and `buildCommand`, and use `railpackConfig` for anything else.

Before:

```yaml
resources:
  web:
    type: web-service
    properties:
      packaging:
        type: nixpacks
        properties:
          sourceDirectoryPath: ./web
          startCmd: node dist/server.js
          phases:
            - name: build
              cmds:
                - npm run build
      resources:
        cpu: 0.25
        memory: 512
```

After:

```yaml
resources:
  web:
    type: web-service
    properties:
      packaging:
        type: buildpack
        properties:
          sourceDirectoryPath: ./web
          startCommand: node dist/server.js
          buildCommand: npm run build
      resources:
        cpu: 0.25
        memory: 512
```

### External buildpacks

Cloud Native Buildpacks and the pack CLI are no longer supported. Try `buildpack`, which detects most projects without configuration. If you depended on a specific builder or buildpack, write a Dockerfile and use `dockerfile`.

Before:

```yaml
resources:
  web:
    type: web-service
    properties:
      packaging:
        type: external-buildpack
        properties:
          sourceDirectoryPath: ./web
          builder: paketobuildpacks/builder-jammy-base
      resources:
        cpu: 0.25
        memory: 512
```

After:

```yaml
resources:
  web:
    type: web-service
    properties:
      packaging:
        type: buildpack
        properties:
          sourceDirectoryPath: ./web
      resources:
        cpu: 0.25
        memory: 512
```

### Custom Dockerfiles

Rename the type to `dockerfile`. The properties are unchanged.

Before:

```yaml
resources:

    type: worker-service
    properties:
      packaging:
        type: custom-dockerfile
        properties:
          buildContextPath: ./worker
          dockerfilePath: Dockerfile.prod
      resources:
        cpu: 0.5
        memory: 1024
```

After:

```yaml
resources:
  worker:
    type: worker-service
    properties:
      packaging:
        type: dockerfile
        properties:
          buildContextPath: ./worker
```

### Removed packaging properties

- `languageSpecificConfig`: its options are direct properties of `js-bundle`, or `python`, `java` and `dotnet` on the Lambda `buildpack`.
- `pythonVersion`, `javaVersion`, `rubyVersion` and `dotnetVersion` on Lambda functions: set the function's `runtime`.
- `packageManager`, `minify` and `runAppAs` for Python Lambda functions.
- `entryfilePath`, `runAppAs`, `languageSpecificConfig`, `requiresGlibcBinaries` and `customDockerBuildCommands` for non-JavaScript container services. Use `sourceDirectoryPath`, `startCommand`, `aptPackages` or a Dockerfile.
- `startCmd`, `phases`, `providers`, `buildImage`, `startRunImage` and `startOnlyIncludeFiles` from `nixpacks`. Use `startCommand`, `installCommand`, `buildCommand`, `aptPackages` or `railpackConfig`.
- `builder` and `buildpacks` from `external-buildpack`.
- PHP Lambda functions. Run PHP as a container with [`buildpack`](/packaging/containers/buildpack).
