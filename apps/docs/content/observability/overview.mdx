# Observability overview

Your functions, containers and databases send logs and metrics to CloudWatch in your own AWS account. Stacktape reads
them for you and adds error tracking, uptime checks, incidents and alerts. This page shows which tool answers which
question, what needs the Stacktape Console, and which data leaves your AWS account.

## Pick a tool

| Question | Tool | Needs the Console |
|---|---|---|
| What did my code print? | [Logs](/observability/logs) | No |
| How busy or slow is a resource? | [Metrics](/observability/metrics) | No |
| Why was this request slow? | [Tracing](/observability/tracing) | To view traces |
| Tell me when a metric crosses a threshold | [Alarms](/observability/alarms) | No, for alerts sent from your account |
| Which exceptions does my code throw? | [Error tracking](/observability/error-tracking) | Yes |
| Is my endpoint up? | [Uptime checks](/observability/uptime-checks) | Yes |
| Does sign-in or checkout still work? | [Synthetic tests](/observability/synthetic-tests) | To view runs |
| What is broken right now, as one problem? | [Incidents](/observability/incidents) | Yes |
| What's inside a running container? | [Debugging containers](/observability/debugging-containers) | No |

Error tracking covers functions packaged by Stacktape and containers packaged with `js-bundle`. It skips workloads
you package yourself, with a Dockerfile, a prebuilt image or a custom artifact, and workloads with log forwarding. For
those, read errors in [Logs](/observability/logs) or keep your own error tracker. See
[which workloads it covers](/observability/error-tracking#how-it-works).

Every CLI command that inspects a stack is listed in [Debug commands](/observability/debug-commands). To send logs to
Datadog, Highlight.io or your own endpoint as well, use [log forwarding](/observability/log-forwarding).

## How alerts reach your team

1. A **signal** fires: an alarm, a failed uptime check or synthetic test, an error in production, an unhealthy stack or
   an expiring certificate.
2. Stacktape groups related signals into one [incident](/observability/incidents), so a bad deploy that causes errors
   and an outage is one problem.
3. [Notification rules](/observability/notifications) choose which [alert channels](/observability/alert-channels)
   get incident, deploy, security and other events: Slack, email, Teams, Discord or a webhook.
4. [Sent alerts](/observability/alert-history) shows everything that was sent and whether it arrived.

Alarms can also notify Slack, Teams, Discord, email or a webhook straight from your AWS account, without the Console.

## Without the Console

With only AWS credentials, you get logs, metrics, alarms with notifications sent from your account, synthetic tests,
tracing data in X-Ray, log forwarding and the debug commands. A deploy whose config uses uptime checks,
`console-channel` or `slack-app` alarm targets, or `deploymentConfig.errorTracking` stops at validation and asks you to
connect the Console. Error tracking stays off until you connect. See
[Use the CLI without an account](/getting-started/open-source-cli).

## What leaves your AWS account

Application logs, build artifacts, dependency lists and secret values stay in your AWS account; the one exception is
the log line of each error that error tracking records. Some features send operational data to Stacktape. Each one is listed below with what it sends, and its own page lists every field.
Before data leaves, known shapes of sensitive text are masked: secrets and tokens, values under keys such as `password`,
email and IP addresses, card numbers and home directory paths. Free text can still carry anything your application
logged, such as names.

The Console keeps what it receives in the AWS `eu-west-1` region (Ireland). Retention differs by feature: error
tracking keeps the newest 100 samples of each issue with no time limit (see
[where errors are stored](/observability/error-tracking#where-errors-are-stored-and-for-how-long)), uptime results are
kept per minute for 48 hours and per hour for 90 days, and [audit events](/stacktape-console/audit-log#how-long-events-are-kept)
for 400 days.

| Feature | What Stacktape receives | Fields |
|---|---|---|
| CLI deploys while signed in | The command, target, Git branch and commit, CLI version, timing, result and the flags that name the target. No free-form flag values, secrets or keys. | [Activity](/stacktape-console/console-overview#viewing-deployment-activity) |
| Error tracking | Each error's message, type, stack frames, its masked log line, request ID and location | [Error tracking](/observability/error-tracking#what-leaves-your-aws-account) |
| Alarms | State changes of alarms with history: name, condition, state and resource | [Alarms](/observability/alarms#what-leaves-your-aws-account) |
| Uptime checks | Check definitions and each probe's status, timings, failure reason and certificate expiry. No response bodies. | [Uptime checks](/observability/uptime-checks#what-leaves-your-aws-account) |
| Synthetic tests | State changes of the test's alarm. Results, screenshots and logs stay in your account. | [Synthetic tests](/observability/synthetic-tests#what-leaves-your-aws-account) |
| Logs, metrics and traces in the Console | Nothing is stored: your browser reads them from AWS with short-lived credentials | [Logs](/observability/logs#read-logs-in-the-console) |
| Costs | A monthly cost breakdown of each connected AWS account, from its AWS cost report | [Cost dashboards](/managing-costs/dashboards) |
| Security scanning | Configuration findings and where the dependency list is. Package names and versions go to OSV.dev; found vulnerabilities are stored. | [Security scanning](/stacktape-console/security-scanning#what-leaves-your-aws-account) |
| Incident briefings, with an AI API key connected | A masked snapshot of what Stacktape already stores about the incident, sent to the provider of your organization's key. No logs or source code. | [Incident AI](/observability/incident-ai#what-leaves-your-aws-account) |
| AI investigations and fixes, when you start one | What the agent reads, including your source code and command output, sent to the agent's provider under your credential | [Incident AI](/observability/incident-ai#what-leaves-your-aws-account) |
| Slack app | What the cards show. Logs are never posted. | [Alert channels](/observability/alert-channels#what-stacktape-sends-to-slack) |
| `stacktape init` | The generated config and region, for the price estimate. A coding agent sends the files it reads to its own provider. | [init](/cli/init#who-reads-your-code-and-what-leaves-your-machine) |
| CLI telemetry | Command names, results and system details; when signed in, also option names and crash reports. Off with `STP_DISABLE_TELEMETRY=1`. | [Telemetry](/getting-started/open-source-cli#telemetry) |

The Console connection itself is an IAM role in your account that Stacktape assumes with short-lived credentials. See
[AWS permissions](/stacktape-console/aws-permissions).
