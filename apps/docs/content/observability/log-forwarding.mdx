# Log forwarding

Log forwarding sends the logs of a function or container to Datadog, Highlight.io or any HTTPS endpoint, in addition to
CloudWatch. Stacktape creates an AWS Kinesis Data Firehose delivery stream for the resource, subscribes the resource's
log group to it, and keeps logs that can't be delivered in an S3 bucket. All of it runs in your AWS account.

Use it when your team already reads logs in another tool. To view and search logs, the Console and
[`stacktape logs`](/cli/logs) need no forwarding. Firehose costs about $0.03 per GB forwarded, depending on the region.

A forwarded log group has no room for the [error tracking](/observability/error-tracking) subscription, so error
tracking skips resources with log forwarding.

## Supported destinations

Set `logForwarding` in the resource's `logging` block. Use the `datadog` or `highlight` type for those services, and
`http-endpoint` for anything else that accepts Firehose deliveries over HTTPS, such as Grafana Cloud, Splunk, New Relic
or your own collector.

| Destination | `type` | Required | Optional |
|---|---|---|---|
| Datadog | `datadog` | `apiKey` | `endpointUrl` (EU accounts) |
| Highlight.io | `highlight` | `projectId` | `endpointUrl` |
| Any HTTPS endpoint | `http-endpoint` | `endpointUrl` | `accessKey`, `gzipEncodingEnabled`, `retryDuration`, `parameters` |

Forwarded log groups need the default Standard log class: Stacktape refuses `logForwarding` together with
`logClass: infrequent-access`, because AWS can't subscribe such a log group.

## Forwarding to Datadog

The `datadog` type needs only `apiKey`. Datadog bills its own ingestion and retention on top of Firehose.

## Forwarding to a custom HTTP endpoint

The `http-endpoint` log forwarding type forwards logs to any HTTPS endpoint that accepts Firehose delivery. This is the most flexible option and the one to use when your destination is not Datadog or Highlight.io — for example, a self-hosted ingestion API or a third-party observability platform that supports Firehose HTTPS delivery.

<CodeBlock
  intellisense

### Configuration properties

- **`endpointUrl`** (required) — the HTTPS URL where Firehose delivers log batches. Must use HTTPS.
- **`accessKey`** — an authentication credential sent in the `X-Amz-Firehose-Access-Key` HTTP header. Store it as a [`$Secret()`](/configuration/secrets) to avoid exposing credentials in your config file.
- **`gzipEncodingEnabled`** — compress the request body with GZIP before delivery. Defaults to `false`. Enable this to reduce transfer volume, but only when your endpoint documents support for GZIP-encoded request bodies.
- **`retryDuration`** — total time in seconds that Firehose retries failed deliveries before routing logs to the backup S3 bucket. Defaults to `300` (5 minutes). Lower values reduce how long logs stay in limbo during outages; higher values give transient failures more time to recover.
- **`parameters`** — key-value pairs sent as metadata in the `X-Amz-Firehose-Common-Attributes` header. Use them only if your destination documents support for Firehose common attributes — for example, routing logs to different indexes based on a header value.

### When to use each property

Most setups need only `endpointUrl` and `accessKey`. Add `gzipEncodingEnabled: true` when you forward high-volume logs (tens of GB/month) to reduce transfer costs. Add `parameters` only when your ingestion endpoint documents support for Firehose common attributes and uses header metadata for routing. Reduce `retryDuration` below 300 when you prefer faster failover to S3 backup over longer retry windows.

## When delivery fails

Firehose retries a batch that the destination refuses or doesn't answer, then writes it to the resource's failed-events
bucket, named `<stack name>-<resource name>-logs-<hash>` (shortened to fit 63 characters). Nothing is lost, but nothing
re-sends it to the destination either.

| Destination | Retries for |
|---|---|
| `datadog` | 60 seconds |
| `highlight` | 300 seconds |
| `http-endpoint` | `retryDuration`, 300 seconds by default |

When logs stop arriving, check the destination's own ingestion errors (a wrong API key or project ID shows up there),
then look for new objects in the failed-events bucket in the S3 console. The resource's logs are still in CloudWatch the
whole time.

## FAQ

### Can I forward only some logs?

No. Every log line of the resource is forwarded. Filter in the destination, for example with Datadog log pipelines.

### Which resources support log forwarding?

Functions and containers that have a `logging` block with `logForwarding`. The API reference of each resource type
shows whether it has the property.
