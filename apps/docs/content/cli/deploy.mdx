# deploy

The `stacktape deploy` command deploys your stack to AWS. If the stack does not exist yet, it creates a new one. If it already exists, it updates it with the current configuration. This is the primary command for shipping changes to any stage — development, staging, or production.

## Usage

```bash
stacktape deploy --stage <stage> --region <region>
```

The CLI needs a stage and a region, so the flag list marks both required. The stage can also come from [`defaults set`](/cli/defaults-configure). Without `--region`, Stacktape uses the first region it finds in the config's `region`, `AWS_DEFAULT_REGION`, `defaults set` or your AWS profile, and asks in a terminal. The command requires a valid Stacktape configuration file (usually `stacktape.ts`, with `stacktape.yml` still supported) in the current directory, or a path passed with `--config`.

```bash
stacktape deploy --stage production --region eu-west-1 --config ./infra/stacktape.ts
```

## What happens during deploy

1. **Validate** — Reads your config and validates guardrails. Asks before an update deletes or replaces stateful resources, and asks for missing secret and SSM parameter values; database passwords are generated. For CI, see [this example](#non-interactive-deploy-in-cicd).
2. **Build & package** — Packages workloads for deployment. Cached artifacts are reused when possible.
3. **Upload** — Uploads deployment artifacts for the stack.
4. **Deploy** — Creates or updates a CloudFormation stack. When only code changed, updates the changed functions and container services directly instead (see [Fast deployments](#fast-deployments)). [Release commands](/deployment-and-lifecycle/release-commands) that are due, such as database migrations, run before the workloads that depend on them get the new code. A failed command stops the deploy.
5. **Post-deploy** — Syncs hosting buckets, invalidates CDN caches, and prints resource URLs.

After a successful deploy, Stacktape prints short stack information and completion links, including a Stacktape Console URL for the deployed stack when you use the Console.

## Fast deployments

When only the code of functions or container services changed, `stacktape deploy` updates them directly instead of through CloudFormation. A function update takes seconds; a container service runs a normal rolling deployment. Stacktape decides this on its own for every deployment, using CloudFormation whenever anything else changed. It prints the reason when it does.

Code that several functions share is packaged into a Lambda layer. A change to it is a code change too: Stacktape publishes the new layer version itself and gives every function that uses it the new version together with its own code, so a change to shared code deploys as fast as a change to one function.

When both a handler and its shared code change, Stacktape attaches the new layer before switching the handler if the old handler can use it. This includes adding a helper and using it in the new handler. When compatibility cannot be proved, Stacktape temporarily keeps both generations available. A failed code update can leave the old handler on the new layer; deploying again completes the update.

The compatibility check protects the forward deployment. CloudFormation updates code and layers separately during a rollback, so rolling back across an edit that added a used export can briefly fail invocations if the old layer is restored before the new handler is replaced. Stacktape prints a note during the fast deployment when it detects this risk. See [rollback safety](/cli/rollback#safety-warnings).

A deployment uses CloudFormation when:

- the stack is new, or the template changes anything other than function code or container images built by Stacktape (configuration, environment variables, permissions, resources, external images),
- stack settings changed, such as tags or termination protection,
- a changed function uses an alias (`deployment` or provisioned concurrency) or a changed container service uses blue/green deployment,
- the stack has an `after:deploy` [deployment script](/resources/advanced/deployment-scripts), which runs through CloudFormation on every deployment,
- you pass `--full`.

A fast deployment is a release like any other: it gets the next version number, and [`rollback`](/cli/rollback) can return to it or from it. A deployment that changes nothing creates no release, even with `--full`. If some updates fail, Stacktape still finishes the others and lists which workloads run the new code. Deploying again updates the rest. The CloudFormation template is updated by the next full deployment.

For eligible Node.js and Python web services on x86 Fargate, `properties.codeSwap: true` enables [in-place code swaps](/deployment-and-lifecycle/code-swap) with the same deploy command ([limits](/deployment-and-lifecycle/code-swap#supported-services)). The opt-in applies in every stage, including production, within the task cap. Failed memory screening or an unsupported change uses an image deploy, with the reason in CLI output. Old and new processes share memory during a swap; a sudden memory increase can fail in-flight requests.

When the build is the slow part, [`--runner ec2`](#--runner) builds and deploys on your project's EC2 runner. See [Deployment is slow](/deployment-and-lifecycle/deploying-stacks#deployment-is-slow) for more causes.

## Common flags

### `--full`

Deploys every change through CloudFormation, even when only code changed.

```bash
stacktape deploy --stage production --region eu-west-1 --full
```

### `--yes`

Confirms the deploy when it needs confirmation: an update that may delete stateful resources, or a project that does not exist yet and would be created. Use `--yes` in CI/CD pipelines and other non-interactive runs. Without it, such a deploy fails with `CONFIRMATION_REQUIRED` before it changes anything. `--agent` only switches the output to JSONL; it does not confirm.

```bash
stacktape deploy --stage production --region eu-west-1 --yes
```

### `--auto-rollback`

By default, a failed deployment keeps what it created or updated. The stack stays in `CREATE_FAILED` (first deployment) or `UPDATE_FAILED` (update), and running `deploy` again after fixing the error continues from the failure instead of creating everything again. A failed update that replaces a resource rolls back anyway. Any failed deployment rolls back when you configure rollback alarms (`deploymentConfig.triggerRollbackOnAlarms`) or a monitoring period above zero (`monitoringTimeAfterDeploymentInMinutes`). With `--auto-rollback`, CloudFormation undoes this deployment if it fails: an update returns to the last successful deployment, and a first deployment deletes the new stack. The flag overrides `deploymentConfig.autoRollback` for one deployment.

```bash
stacktape deploy --stage production --region eu-west-1 --auto-rollback
```

To undo a failed update later, use [`stack recover`](/cli/cf-rollback). To remove a failed first deployment, use [`delete`](/cli/delete). To return to an earlier successful version, use [`rollback`](/cli/rollback). See [when a deployment fails](/deployment-and-lifecycle/deploying-stacks#when-a-deployment-fails).

### `--no-cache`

Forces a fresh build of all compute resources, ignoring cached artifacts from previous deploys. Use this when you suspect a stale cache is causing issues.

```bash
stacktape deploy --stage dev --region eu-west-1 --no-cache
```

### `--config`

Points to a Stacktape configuration file when it is not in the default location (current directory).

```bash
stacktape deploy --stage production --region eu-west-1 --config ./infra/stacktape.ts
```

### `--no-layer-optimization`

By default, Stacktape extracts shared code into Lambda layers to reduce per-function deployment size. Disable this to bundle all code directly into each Lambda function — useful if you need to inspect the full function package or if layer extraction causes issues.

### `--skip-release-command`

Deploys without running the [release commands](/deployment-and-lifecycle/release-commands#skipping-and-interrupting). Use it when you already ran the command yourself, or to deploy a fix for the command. The next deploy without the flag runs it if it is still due.

### `--runner`

`--runner ec2` runs the build and deployment on the project's [EC2 runner](/ci-cd-and-gitops/build-runners) in your AWS account instead of your machine. It deploys the current Git commit, so uncommitted changes are left out. The runner currently ignores `--skip-release-command`, `--no-cache`, `--no-remote-cache` and `--no-layer-optimization`. It needs a Stacktape Console sign-in and does not accept `--auto-rollback`; set `deploymentConfig.autoRollback` in the config instead.

```bash
stacktape deploy --stage production --region eu-west-1 --runner ec2
```

### `--no-remote-cache`

In CI, image builds for an existing stack keep Docker's layer cache in the stack's ECR repository, so a fresh CI machine still reuses unchanged layers. Outside CI, Docker's local cache is used. Pass `--no-remote-cache` to skip the ECR cache in CI.

### `--show-secrets`

Includes secret values, such as database passwords and connection strings with credentials, in the `--agent` result (`data.result.stackInfo`) and in the stack-info file. Without it, each of them is `<<OMITTED>>`. Use it only where the output stays private, never in shared CI logs. The terminal summary never prints secret values.

## Examples

### Deploy a new production stage

```bash
stacktape deploy --stage production --region us-east-1
```

### Deploy to the account of an AWS profile

The deploy goes to the AWS account that `my-aws-profile` belongs to. When the CLI is signed in to the Console, that account must be connected to your organization, or the deploy fails.

```bash
stacktape deploy --stage staging --region eu-west-1 --profile my-aws-profile --project my-app
```

### Deploy to a named connected account

With the Console, choose one of the organization's connected AWS accounts by name.

```bash
stacktape deploy --stage production --region eu-west-1 --aws-account production
```

### Deploy through CloudFormation

```bash
stacktape deploy --stage production --region eu-west-1 --full
```

### Non-interactive deploy in CI/CD

```bash
stacktape deploy --stage production --region us-east-1 --yes
```

The CI job needs AWS credentials, or a Stacktape API key when you use the Console; see [authentication in CI](/ci-cd-and-gitops/custom-ci-cd#authentication). Database passwords are generated. Create the other secrets and SSM parameters the config uses with [`secret set`](/cli/secret-set) or in AWS before the first run: a missing one fails the deploy. If a deploy of the stage is already running, the next one [waits for it](/ci-cd-and-gitops/custom-ci-cd#concurrent-deploys-to-the-same-stage); two first deploys of a new stage can't wait, and one of them stops.

### Preview changes before deploying

Use [`diff`](/cli/diff) to see what a deploy would modify without actually applying changes:

```bash
stacktape diff --stage production --region us-east-1
```

Stacktape does not currently check CloudFormation resource drift before deploying. Manual changes to stack resources can affect an update; review the proposed changes with [`diff`](/cli/diff).

## Free plan cost limit

Deploys pause when a Free organization’s managed AWS costs for the current calendar month (UTC) are above $200
and its grace period no longer applies. The one-time grace lasts up to seven days and applies only in the UTC month it starts. The CLI stops before changing your stack and prints a
`Free Plan Limit Reached` error with this month’s costs, the limit and the link to upgrade.

```text
[x] Free Plan Limit Reached

Deploys are paused. This organization is on the Free plan, and the AWS costs Stacktape manages for it are
$242.17 in October 2026 (UTC), above the plan's limit of $200 a month.
```

Upgrading to the Flexible plan lifts the limit immediately; otherwise deploys resume when the next month starts.
[`delete`](/cli/delete) and [`rollback`](/cli/rollback) keep working, and running infrastructure is not affected. See
[Free plan cost limit](/stacktape-console/billing-and-subscription#free-plan-cost-limit) for what counts.

## Dev stacks cannot be deployed

Stages created by [`stacktape dev`](/cli/dev) (dev stacks) cannot be updated with `deploy`. If you attempt this, Stacktape rejects the deploy with an error. To deploy a production stack, use a different stage name (e.g., `--stage production`). To remove a dev stack, use [`stacktape delete`](/cli/delete).
